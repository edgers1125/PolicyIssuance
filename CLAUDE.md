# PolicyIssuance

Insurance policy/quotation issuance app for Bethel General Insurance and Surety Corp.

## Stack

- **backend/**: Express 5 + Prisma 7 (PostgreSQL, `@prisma/adapter-pg`) + JWT auth (`jsonwebtoken`) + `zod` v4 validation. CommonJS (`require`).
- **frontend/**: React 19 + Vite + MUI 9 (`@mui/material`, `@mui/icons-material`). No Tailwind, no shadcn. React Router 7.
- No tRPC, no shared package — frontend calls backend REST via a hand-written `fetch` wrapper (`frontend/src/api/client.js`).

## Dev environment — Docker Compose

`docker-compose.yml` at repo root runs 4 services: `db` (postgres:16, port 5432), `backend` (port 4000), `frontend` (port 5173), `prisma-studio` (port 5555). Container names: `policyissuance-backend-1`, `policyissuance-frontend-1`, `policyissuance-db-1`, `policyissuance-prisma-studio-1`.

**Gotcha**: `backend`/`frontend`/`prisma-studio` node_modules are named Docker volumes, *not* bind-mounted from the host. Running `npm install <pkg>` on the host updates `package.json`/`package-lock.json` (bind-mounted) but **does not** reach the container's node_modules. After adding a dependency, restart the container to re-run its `npm install && npx prisma generate && npm run dev` start command:
```
docker restart policyissuance-backend-1
```
Source is bind-mounted with `CHOKIDAR_USEPOLLING=true` (Windows host, nodemon/Vite poll instead of relying on inotify).

`.claude/launch.json` points `preview_start` at `npm --prefix backend/frontend run dev` — if the Docker containers are already up on those ports, `preview_start` fails with "port in use"; just `navigate` to `http://localhost:5173` directly instead of starting a second copy.

**Local test login**: seed script (`backend/prisma/seed.js`) creates `admin@policyissuance.local` / `Password123!`, but the dev DB may have different data/passwords already. Check first: `docker exec policyissuance-db-1 psql -U policyapp -d policyissuance -c "select id,email,agent_id from \"User\";"`. To test API/UI without knowing a password, mint a JWT directly with the `JWT_SECRET` from `backend/.env` (payload shape `{ userId, email }`, see `backend/src/utils/jwt.js`) and inject it into the browser's `localStorage` (`token` + `user` keys, see `AuthContext.jsx`).

## Validation contract — read before touching any route

**Every backend route's `body`/`query`/`params` is validated by a zod schema via `validateBody`/`validateQuery`/`validateParams` (`backend/src/middleware/validate.js`).** Convention: **one schema file per route file, same name** (`routes/policyQuotations.js` ↔ `schemas/policyQuotations.js`), imported directly into the route. Shared cross-route building blocks live in `schemas/common.js` (`requiredString`, `requiredEmail`) and `schemas/policyIntakeShared.js` (address/vehicle/coverage input shapes + refinements shared by applications and quotations).

**Rule: any time a route's accepted input changes (new field, renamed field, changed type, new endpoint, new required-ness), its zod schema must be updated in the same change — never let a route accept something its schema doesn't describe, and never leave a schema describing a field the route no longer reads.** This includes new `:id`/query params (add a param schema, validate with `validateParams`/`validateQuery`) and new refinements when a field's validity now depends on another field. Zod v4 syntax is used throughout (`z.coerce.date({ error: "..." })`, not `required_error`).

**`routes/endorsements.js`** — router-level `requireAuth` only; each route below applies its own grant, since an agent filing an endorsement (`VIEW_POLICIES.CREATE_ENDORSEMENT`) and an approver reviewing one (`APPROVE_ENDORSEMENT`) are different tiers a caller may hold only one of. An `EndorsementRequest` is one of two kinds (`request_type: EndorsementRequestType`): a **CORRECTION** (the default — one or more `EndorsementChange` lines) or a **CANCELLATION** (exactly one server-synthesized `CANCEL_POLICY` line, no others). Most `EndorsementChangeType` values are still corrections-only and *never* write onto the `Policy`/`PolicyVehicle`/`PolicyAddress` rows — every read of that policy (`GET /policies/:id`, its PDF, resend-email) folds them back in at read time (`routes/policies.js`'s `applyEndorsementsToPolicyDetail`/`foldEndorsementChanges`/`applyFoldedState`, all three exported from that file for reuse here). Three values ARE financial and DO produce a real, permanent effect once approved — see `EndorsementChangeType`'s own comment (enums.prisma) for the full design:
- **`ADD_COVERAGE`** — prices a brand-new coverage through the exact same `lib/coveragePricing.js` engine an application/quotation uses (`priceAddCoverageChange()`, called from `resolveEndorsementChange()` at filing time, not re-priced at approval), then on approval actually creates a new `PolicyCoverage` row and credits the filing agent's payable ledger (`AgentPayableTransaction`, `transaction_type: "ENDORSEMENT"`, positive) with that row's own margin.
- **`REMOVE_CLAUSE`** — repurposed from "remove text from a coverage's clause" (that's `EDIT_CLAUSE`'s job now) to "remove this coverage line entirely": soft-deletes the targeted `PolicyCoverage` (`removed_at`/`removed_by_endorsement_id`) and debits the ledger (`ENDORSEMENT`, negative) by the margin that coverage had contributed — `change_from`/the removal amount are frozen onto the `EndorsementChange` row at filing time, not re-read at approval.
- **`CANCEL_POLICY`** — the sole line on a `CANCELLATION` request; on approval sets `Policy.policy_status = CANCELLED` + `Policy.cancelled_at` and debits the ledger (`CANCELLED_POLICY`, negative) with a **day-prorated refund** of the commission already earned on that policy (`computeCancellationProration()`, computed fresh at approval time — never trusted from filing — off `SUM(AgentPayableTransaction.amount) WHERE policy_id = ... AND transaction_type IN ('ISSUANCE','ENDORSEMENT')`, the policy's current folded effective/expiry dates, and the cancellation's own `effective_date`; the exact days-used/days-remaining/daily-rate breakdown is written into the ledger row's own `remarks` for auditability). A cancelled policy can never be endorsed again (`POST /` 400s once `policy_status === "CANCELLED"`).

### Shared application/quotation intake logic

`POST /policy-applications` and `POST /policy-quotations` share one pattern (applications add payment fields on top):
- Constants: `DOC_STAMPS_RATE = 0.125`, `VAT_RATE = 0.12`, `LGT_RATE = 0.002`.
- Number generator: `APP-{YYYYMMDD}-{6 hex}` / `QUO-{YYYYMMDD}-{6 hex}` (`crypto.randomBytes(3)`).
- `insured_type` is **derived server-side** from whichever of `customer_id`/`company_id` was sent, never trusted from the client.
- `className` (from `product_variant.insurance_class.class_name`) drives conditional requirements: Motor needs ≥1 vehicle; Property needs `risk_address`; Motor or Property needs `insured_address`.
- Ownership check: acting agent must have a `CustomerAgent`/`CompanyAgent` link to the insured party (403 otherwise) — for a company, this also honors `lib/agent.js`'s `getAccessibleAgentIds()` (a company linked to the agent's own parent `CORPORATE` agency counts too, see `Agent.linked_company_id`), same widened check `routes/companies.js`'s own `GET /`/`PATCH /:id` apply.
- Vehicle values for `VALUE_PERCENTAGE` pricing resolved via `currentVehicleValue()` (depreciation); for Property (no vehicles), the same pricing mode instead resolves off the risk address's own `Address.estimated_value` (no depreciation — a property's value doesn't automatically decay the way a vehicle's does), looked up fresh from the DB for a reused address or taken from what was just entered for a new one, mirroring the vehicle-value lookup split. Passed into `resolveCoverageRows` as `addressValue`.
- Coverage pricing/validation delegated to `resolveCoverageRows()` (`lib/coveragePricing.js`) — shared engine, throws `HttpError`. Each resolved row's `is_misc` flag (see `ProductCoverage.is_misc`, Pricing catalog section above) then splits the sum into `total_premium` (non-`is_misc` rows only) and `misc` (`ProductVariant.misc_fee` plus every `is_misc` row's premium) — `doc_stamps`/`vat`/`lgt` still tax the full, unsplit sum regardless. `PATCH /policy-quotations/:id` re-derives this same split on every coverage edit (and now writes `misc` back, unlike before this flag existed — a quotation's coverages, unlike its fixed `product_variant_id`, genuinely can change here).
- Single `prisma.$transaction`: creates the header row, resolves each vehicle (reuse / reassign-to-this-party / create-new), creates coverage line rows, resolves risk/insured addresses (reuse or create; `estimated_value` persisted on a newly created address).
- **Vehicle value/date freeze rule** (also enforced in `PATCH /vehicles/:id`): once `initial_assessment_date` is set, it and `estimated_value` are never directly overwritten again — value only changes via automatic depreciation. No equivalent freeze exists for `Address.estimated_value` — it can be revised directly at any time via `PATCH /addresses/:id`.
- **Vehicle plate-number immutability**: a vehicle's `plate_number` is a fixed real-world identifier and is never overwritten as a side effect of anything else — the `reassign_owner: true` branch of both create transactions (a vehicle matched by plate to a *different* party, being moved over — see `PlateConflictDialog`/`handleConfirmPlateMatch` in the frontend) updates every other field the agent may have corrected but deliberately omits `plate_number` from the `tx.vehicle.update` call, regardless of what the client sent. The only legitimate way to change it is `PATCH /vehicles/:id` (see its own entry above, which re-checks uniqueness). Frontend-side, both wizards' inline vehicle-row Plate Number field is `disabled` once a row has `existing_vehicle_id` set (whichever way it got matched) — a mismatched match is undone via "Use a different vehicle" (`resetVehicleRow`), not by typing over the field, and `VehicleEditDialog`'s own Plate Number field is additionally disabled in `localOnly` mode (a vehicle pending reassignment) since the backend won't honor a change there anyway.
- **`Vehicle.no_of_seats`** is required on every vehicle create/reassign-update in both transactions (`vehicleInputSchema`) — not part of the freeze rule above, always writable. Feeds the policy schedule's "1 DRIVER AND N OCCUPANTS OR PASSENGERS" endorsement line (see "PDF generation" below), off the *first* vehicle on the schedule.
- **`Vehicle.product_variant_id` consistency**: every vehicle on one Motor application/quotation must resolve to the same `product_variant_id` as the filing's own top-level field — for a reused vehicle this is whatever's already on its `Vehicle` row (never trusted/overwritten from the client here; only `PATCH /vehicles/:id` can actually change it), for a brand-new one it's `vehicleInputSchema`'s own required `product_variant_id`. Both create routes 400 on a mismatch (`"All vehicles on this application/quotation must be insured under the same product variant"`). This is what let the **Product Variant wizard step be removed for Motor entirely** — see `PolicyApplication.jsx`/`QuotationCreator.jsx` below: the variant is now derived from whichever vehicle establishes one, collected inline as part of the Vehicles step instead of its own step-after. Property is unaffected (still its own explicit step, right after Risk Address, since it has no vehicles to derive one from).

### PDF generation (`src/pdf/`) — standard going forward

**Every policy/quotation document (preview, export, email attachment) is generated server-side with PDFKit, in its own file under `backend/src/pdf/`.** This is a project-wide rule, not just how quotations happen to work: any future document type (an eventual issued-`Policy` PDF, etc.) gets its own `backend/src/pdf/<name>Pdf.js` following the same pattern — not a browser-print/`window.print()` flow, and not Puppeteer/headless-Chrome (this container has no Dockerfile, so Chromium's system libraries — `libnss3`, `libatk-1.0-0`, etc. — aren't installed and never get a chance to be; Puppeteer would crash at launch here).

- **`pdf/theme.js`** — the only genuinely shared plumbing: `FONT_BODY`/`FONT_BODY_BOLD` (PDFKit's standard-14 `Times-Roman`/`Times-Bold` — see the font-choice note below for why these, not an embedded font, are used for body text), `FONT_WATERMARK` (`Helvetica-Bold`, matching the HTML mockup's `Arial, sans-serif` bold — deliberately a different, sans-serif family, since a watermark/rubber-stamp is meant to read as a separate annotation layered on top of the typeset document, not as part of its body text), `BASE_FONT_SIZE` (9.5 — a compact, professional body size for a dense legal/insurance form; printed policy schedules typically run 9–10pt, not a web page's 12px), `registerFonts(doc)` (registers only the currency-only `"Peso"`/`"Peso-Bold"` DejaVu Serif fonts — `Times-Roman`/`Times-Bold` are PDFKit standard fonts, always available without registration), `formatMoney`/`fmtDate`/`fmtDateTime`, `drawCurrency`/`drawCurrencyInline` (see the font-choice note below), `drawLogoWatermark`, `drawDiagonalStamp`, `drawSignatureBlock(doc, x, y, width, { signed })`, `SIGNATURE_BLOCK_HEIGHT` (the block's total drawn height — callers use it to reserve room above the page's bottom margin before drawing the block, see the signature note below), `labelValue`, `TOWING_AMOUNT` (`500` — a fixed peso amount, never a rate, applied identically at every stage: quotation, application, and issued policy alike), `computeDeductibleFigures(amount, deductibleRate)` (pure numeric helper, not layout — `{ deductible, authorizedRepairLimit }`; `deductible` is `null` when `deductibleRate` isn't configured, and `authorizedRepairLimit` is simply `deductible + TOWING_AMOUNT` — there's no separate authorized-repair-limit rate any more, see the Coverage sections bullet below for why this changed).
- **`pdf/letterhead.js`** → `drawLetterhead(doc, x, y, width)` — the single source of truth for the Bethel masthead (shield logo + "BETHEL"/"Life and General Insurance Corporation" wordmark on the left, the former-name/address/contact small print right-aligned on the right, closed off by one navy rule) drawn once at the top of every document's first page, before its own title block. Returns the y-coordinate the caller's own title block should start at, so a rebrand or contact-detail change is a one-file edit that reaches every document type — kept as its own file rather than folded into `theme.js` specifically so it stays that single, obviously-complete edit target. Not redrawn on later pages (the clause page, or an overflow page) — only the masthead's own first page carries it, same as the title text itself. The logo is vertically centered against the two-line wordmark as a whole block (measured via `doc.heightOfString()` rather than assumed font metrics, so it stays correct if either line's font size ever changes) and sits close beside it (`LOGO_TEXT_GAP`/`WORDMARK_LINE_GAP`, both intentionally tight) rather than both simply starting flush at the same `y` — which only lined up their tops, not their true centers, and left a wider gap than the lockup was meant to have.
- **Font choice — body text is Times-Roman/Times-Bold (standard-14 AFM fonts), currency alone is DejaVu Serif (`"Peso"`/`"Peso-Bold"`)**: this project briefly tried unifying the *entire* document onto one embedded DejaVu Serif family (to fix price text visually mismatching the surrounding body font), but that introduced a much worse, genuinely broken-looking defect and was reverted — kept here so it doesn't get re-attempted the same way. DejaVu Serif's embedded kerning data is applied by fontkit's glyph-layout engine **regardless of the `.text()` `features` option** (confirmed by testing `{features: ["-kern"]}` and even `{features: []}`, a full OpenType-feature opt-out — neither changed the output at all, proving the adjustment isn't coming from a togglable GSUB/GPOS feature), and for ordinary body-length text it produces wildly oversized position adjustments on certain letter pairs — e.g. "PARTY" rendering with a visible gap inside the word. Confirmed by inspecting the PDF's own decompressed content stream directly: DejaVu Bold's `TJ` adjustments ran 70–175 units for pairs like "P-A"/"R-T", versus Times-Bold's normal 20–75-unit kerning for the identical text (Times-Roman/-Bold use PDFKit's separate, well-tested AFM-kerning-table code path, not fontkit's TTF layout engine, and never exhibited this). The defect is specific to **pdf.js's canvas rendering** (`components/PdfViewer.jsx`, used for every in-app inline preview) — it did not show up when re-verified via the Read tool's own PDF rendering or a native PDF viewer's "Print / Save as PDF" export, which is exactly why it read as "the exportable PDF looks fine but the preview looks bad." Short numeric/currency strings (digits, peso sign, comma, period) never triggered it in any test — confirmed clean — so DejaVu Serif stays scoped to currency only, same as the project's original approach: `drawCurrency`/`drawCurrencyInline` draw a peso amount's *entire* `"₱1,234.56"` string in one call in `"Peso"`/`"Peso-Bold"` at `BASE_FONT_SIZE * PESO_FONT_SIZE_SCALE` (DejaVu Serif's glyphs render visibly larger than Times-Roman's at the same nominal size, so this correction keeps a price visually flush with the Times-set label beside it), then restore the caller's Times font/`BASE_FONT_SIZE`. **Known limitation of the DejaVu currency fonts specifically, deliberately not worked around**: their ligature substitution (fi/fl/ffi) isn't correctly reverse-mapped in the embedded font's ToUnicode CMap (a PDFKit 2.0.4/fontkit limitation; not reachable via `features` or ZWNJ insertion, both tried) — irrelevant for currency strings (no such letter pairs), noted here only because it was investigated during the same debugging pass.
- **`pdf/quotationPdf.js`** → `buildQuotationPdf(props)` — always shows the red diagonal "POLICY NOT IN EFFECT / QUOTATION ONLY" stamp; title "QUOTATION", "Quotation No :", "Date Prepared:".
- **`pdf/policyApplicationPdf.js`** → `buildPolicyApplicationPdf(props)` — title "POLICY SCHEDULE", "Policy No :", "Date Issued:"; shows the same red diagonal `drawDiagonalStamp` watermark mechanism as a quotation's (text "POLICY NOT IN EFFECT / AWAITING APPROVAL") whenever `props.isPreview` is true — which, since an application is never itself the issued `Policy` (see `Policy.application_id`), is every application PDF this builder produces today, live draft or already-saved re-export alike. Never draws a signed signature block (`drawSignatureBlock(doc, x, y, width)`, `signed` omitted/false) — an application, pending or already-approved-but-viewed-through-this-builder, is never the final signed document; see `pdf/policyPdf.js` below for that.
- **`pdf/policyPdf.js`** → `buildPolicyPdf(props)` — the issued `Policy`'s own document (`routes/policies.js`'s `GET /:id/pdf`, and the approval-notification email's attachment). Same "POLICY SCHEDULE" layout as `policyApplicationPdf.js`, with three deliberate differences: never carries the "AWAITING APPROVAL" watermark (a `Policy` only exists once approved, never as a draft, so there's no `isPreview` concept here at all); "Date Issued:" reads `props.issueDate` (the policy's actual `issue_date`) rather than the live render time, so a re-export keeps reading the way it did on the day it was issued; and its signature block is drawn `{ signed: true }` — the real branch-head signature image, not a blank line (see the signature-protection note below). `props.cocNumber`/`props.saNumber`, when present, each grow a second header line — "COC No :" right below "Policy No :", "SA No :" right below "Date Issued:" — since neither has anywhere else to print. `props` shape: `policyNumber, cocNumber?, saNumber?, classNameLabel, variantName, insuredName, insuredAddress, agentCode, issueDate, coverageStartAt, coverageEndAt, vehicles, coverages, deductibleRate, totalPremium, docStamps, vat, lgt, misc, totalAmount, remarks, endorsements` — built by `routes/policies.js`'s `toPolicyPdfProps()` purely off a `Policy` row's own `*_snapshot` columns (already folded through `applyEndorsementsToPolicyDetail()` by every caller), never a live join. After the main schedule (and its clause page, if any), one `pdf/endorsementPdf.js` page (`drawEndorsementPage()`, imported directly rather than duplicated) is appended per `props.endorsements` entry — every `APPROVED` endorsement on this policy, oldest first, always signed and never watermarked — so re-exporting a policy's PDF always carries its own amendment history in the same file.
- **`pdf/endorsementPdf.js`** → `buildEndorsementPdf(props)` (standalone document — `routes/endorsements.js`'s `GET /:id/pdf`/`POST /preview-pdf` and both automatic endorsement emails) and `drawEndorsementPage(doc, props)` (the actual page-drawing function, reused by `pdf/policyPdf.js` to append one page per `APPROVED` endorsement right after the main schedule — see that file's own entry). Title "ENDORSEMENT"; header block mirrors `policyPdf.js`'s own two-column info/charges layout with an added "Endorsement No :" row and "Others" in place of "Miscellaneous" (this template's own wording, per the user-specified layout) — **the charges block (`totalPremium`/`docStamps`/`vat`/`lgt`/`misc`/`totalAmount`) reflects the pricing *change* this endorsement's own `ADD_COVERAGE`/`REMOVE_CLAUSE` lines introduce**, computed by `routes/endorsements.js`'s `computeEndorsementChargeDelta(changes)` (every other change type, including `CANCEL_POLICY`, contributes nothing — its own effect is a ledger debit, not a premium change) — a removal contributes its own `premium_amount` negatively, run through the same `lib/coveragePricing.js` `computeChargeTotals()` split used everywhere else, then totalled. Then "This endorsement is effective: `<effectiveDate>` and expires `<expiryDate>`" (the *policy's* own current expiry, never stored on the endorsement itself); then a numbered amendment list, each entry a bold title line naming the standard endorsement title for that change type (`changeTitle()`, also exported — e.g. "CORRECT PLATE NUMBER", "CORRECT ASSURED", "ADDITIONAL COVERAGE", "DELETION OF COVERAGE", "CANCELLATION OF POLICY", drawn from Bethel's own fixed list of motor-car endorsement titles plus the new financial/cancellation ones) followed by an indented, plain-English From/To narrative underneath it (`describeChange()`, also exported) — e.g. `1. CORRECT COLOR` then, indented, `The color of the vehicle (NCV5516) is corrected (From: "RED" To: "Midnight Blue")`; an `ADD_COVERAGE` line's own narrative is just its already-descriptive `change_to` string verbatim (computed once, at filing, by `priceAddCoverageChange()`); then the fixed "EXCEPT AS HEREIN VARIED..."/"IMPORTANT NOTICE TO THE ASSURED" boilerplate the user specified verbatim; then a "Conforme:" blank signature line (client) beside the usual `drawSignatureBlock` (branch head). `props.stampText` (e.g. "ENDORSEMENT PENDING APPROVAL"/"ENDORSEMENT REJECTED") reuses `theme.js`'s `drawDiagonalStamp`, `null` once `APPROVED`; `props.signed` draws the real branch-head signature only once `APPROVED`, same convention as `policyPdf.js`'s own. `props.changes[]` entries carry pre-resolved `vehicle_label`/`coverage_label` (plate number / coverage name) — this file does no DB lookups of its own, matching every other builder's "props already carry everything" contract. **`drawDiagonalStamp` must be called first, before `drawLetterhead`/any real layout** — this bit once, so it's worth spelling out why: the stamp's own `.text()` call runs inside a rotated+translated CTM (`theme.js`'s `withPageCenterOrigin` — `doc.save()`/`translate()`/`rotate()`/…/`restore()`), and PDFKit's text-flow cursor (`doc.x`/`doc.y`) is a plain instance property, *not* part of the graphics state `doc.restore()` reverts — so calling the stamp any later leaves `doc.y` holding a coordinate from inside that rotated space, and everything positioned off it afterward (the whole two-column info block, via `const infoTop = doc.y`) collapses up into the letterhead. `quotationPdf.js`/`policyApplicationPdf.js` already drew their own stamp first-thing for this exact reason; `endorsementPdf.js` originally didn't (drew it after the title block instead) and every field below the letterhead rendered stacked on top of each other as a result — fixed by moving it back to the front, matching the other two builders.
- **Deliberately duplicated, not shared**: these four files independently implement their own page layout (title block, two-column info/charges table, vehicle table or amendment list, witness/signature block) rather than delegating to one shared renderer — matches how `QuotationCreator.jsx`/`PolicyApplication.jsx` are already two separate, near-identical files rather than one parameterized component. Editing one document type's layout can't accidentally change another's.
- **Manager signature protection (`pdf/assets/manager_signature.png`)**: never served over HTTP — `src/index.js` registers no `express.static` anywhere under `src/` (or anywhere at all), so this file is reachable only by this Node process's own filesystem reads inside `theme.js`'s `drawSignatureBlock()`, never by a public URL. That's the entire protection mechanism, and it's already in place for every asset under `pdf/assets/` (the Bethel logo and DejaVu fonts included) — **do not add a static mount for `src/pdf/assets` (or any `src/` subdirectory)**, since that would make the signature image directly downloadable by anyone with the URL.
- **Signature block layout (`drawSignatureBlock`)** — the company-name line and the printed `BRANCH_HEAD_NAME` line are pulled apart by a named `SIG_NAME_Y` offset specifically to open up a floating gap for the signature image between them, rather than the image sitting cramped on top of the printed name (scaled down alongside `BASE_FONT_SIZE`'s own reduction — see the font-choice note above — so the gap stays proportional to the smaller body text around it, not oversized relative to it). `signed: true` (only ever passed by `pdf/policyPdf.js`) draws the image centered in that gap — sized off a fixed target height (capped to the gap's own clear height, so it can never grow tall enough to collide with either neighboring line regardless of the source image's own aspect ratio) rather than a fraction of the block's own width, and floats there rather than overlapping either line's text — the way a wet-ink signature actually sits above a signature line, not stamped on top of it. Every caller that positions the block near a page's bottom margin must reserve `SIGNATURE_BLOCK_HEIGHT` (the block's own full height, exported from `theme.js`) below its `y` anchor — the three `*Pdf.js` builders' own `sigY` computation additionally clamps between a `sigFloor` (pin the block near the bottom for short content, matching "the on-screen preview's own placement") and a `sigCeiling` a fixed distance above the bottom-margin small print (the "ID No./Agent Code/Time/Date" line) — **don't let `sigY` grow unbounded off `doc.y + 30` alone**; on a page with enough content to push `doc.y` that far down, an unclamped signature block collides with that footer line (this actually happened once, while enlarging the block to make room for the floating signature above — the fix was adding `sigCeiling`, not shrinking the block back down).
- **`renewingPolicyNumber`** (optional, on all three of `quotationPdf.js`/`policyApplicationPdf.js`/`policyPdf.js`'s props): when present, prints a bold "Renewing/Replacing : `<policy number>`" line directly above "Period of Insurance :" (same section, no extra `sectionRule()`) — the connected prior policy this filing continues. Sourced from `PolicyQuotation.renewed_policy`/`PolicyApplication.renewed_policy`'s own live-joined `policy_number` for a quotation/application (`toQuotationDetail`/`toApplicationDetail`), or `Policy.renewed_policy_number_snapshot` for an issued policy (see that field's own entry above) — `undefined`/`null` omits the line entirely for a `NEW_POLICY`. The live-draft "preview-pdf" routes take it as `renewingPolicyNumber` too (`documentPreviewPropsSchema`); `PolicyApplication.jsx` passes its own `renewedPolicyNumber` state (set only via the explicit "Renew This Policy" flow, not the proactive plate-lookup banner) — `QuotationCreator.jsx` has no equivalent yet, so a fresh, not-yet-saved quotation's own live preview never shows this line even when it will turn out to be a renewal (matches `PolicyQuotation.renewed_policy_id`'s own "stays invisible on the quotation itself" design).
- **Canonical prop shape**: both builders take the same props — `applicationNumber, isPreview, classNameLabel, variantName, insuredName, insuredAddress, agentCode, coverageStartAt, coverageEndAt, vehicles, coverages, deductibleRate, totalPremium, docStamps, vat, lgt, misc, totalAmount, remarks, renewingPolicyNumber` (vehicle objects keep the DB's snake_case field names — `plate_number`, `mv_file_no`, `no_of_seats`, etc.; each `coverages[]` entry also carries `pricing_mode`, off `ProductCoverage.pricing_mode`). One shape, two consumers: every PDFKit builder, and the `documentPreviewPropsSchema` validating live draft data over the wire. `policyQuotations.js`'s/`policyApplications.js`'s `toPreviewProps(detail)` map a saved record's DB-flattened detail onto this same shape, including `deductible_rate` off the record's own `product_variant`. (There used to be a third consumer — an HTML component mirroring this shape for an on-screen preview — see "Printing/PDF" below for why that's gone.)
- **Scheduled Vehicle table** — two columns × four rows, identical in all three builders: `Model:`/`MV File No.:`, `Body:`/`Serial No.:`, `Make:`/`Authentication No.:`, `Plate No.:`/`Color:`. These are this document's own labels for existing `Vehicle` fields, not new data — `Model:` reads `year_model` (this schedule's own long-standing convention: "Model" here means the model *year*, matching how a PH OR/CR's own "Model" field reads, not the separate `model` name field, which this schedule has never printed), `Body:` is `vehicle_type`, `Serial No.:` is `chassis_number`, and `Authentication No.:` is `engine_number` — a straight relabel/regroup of the same fields a now-removed three-column layout used to show as "Vehicle type:"/"Chassis No.:"/"Engine No.:".
- **Coverage sections** (the former single "COVERAGES" heading + table is now three sections, identical logic in all three builders): coverages are split by `pricing_mode` — **Section I/II** is a fixed, non-data-driven "THIRD PARTY LIABILITY (Subject to the Schedule of Indemnities) PREMIUMS" header (third-party liability is baked into the base Motor Car policy, not itemized as its own priced row here); **Section III "Insured's Estimate of Value of Scheduled Vehicle"** renders only when at least one coverage has `pricing_mode: "VALUE_PERCENTAGE"` — one block per such coverage row (its `amount` is already that row's targeted vehicle's current depreciated value, computed by `lib/coveragePricing.js`), each showing the estimate-of-value/premium, a static "Limit on Accessories — Standard Built-in Accessories" line, then a `Deductible: ₱x | Towing: ₱500 | Authorized Repair Limit: ₱y` line via `computeDeductibleFigures()`/`TOWING_AMOUNT` (an em dash on Deductible/Authorized Repair Limit when `deductibleRate` isn't configured on the coverage's `ProductVariant` — **Towing is always the same fixed ₱500 at every stage**, never computed off a rate and never blank); **"SECTION IVA, IVB, PA, AOG & OTHERS"** is every other coverage (`PERCENTAGE`/`FLAT_TIER`/`VEHICLE_SEATS_BASED` — the new seat-count mode gets no dedicated section of its own, just a plain row here, same as `FLAT_TIER`), same plain Coverage/Amount Covered/Premium table as before this split existed (a "None" row when there are no such coverages). The Deductible/Towing/Authorized Repair Limit line draws all three peso amounts via `theme.js`'s `drawCurrencyInline()` — same size-corrected DejaVu-for-currency-only handling as `drawCurrency()`, just for an amount flowing inline with label text on a continued-text run instead of sitting in its own right-aligned column (see the font-choice note above).
- **Forms & Endorsements / sea-faring notice** — Motor-specific boilerplate, rendered only when `vehicles.length > 0` (skipped entirely for Property): "1 DRIVER AND N OCCUPANTS OR PASSENGERS AT Php. 50,000.00 EACH" where N is `vehicles[0].no_of_seats - 1` (an em dash if seats is missing/invalid), followed by the fixed sea-faring-vessels/marine-cargo-policy advisory paragraph.
- **Witness paragraph + small print** — "IN WITNESS WHEREOF..." is fixed boilerplate naming Marikina (Bethel's branch city, hardcoded same as `theme.js`'s `BRANCH_HEAD_NAME`) and today's date (`fmtDate(new Date())` — the render date, not a stored "policy date" field); immediately followed by the existing Documentary-Stamps-paragraph/signature-block split (unchanged), then a small 8pt bottom-left line — `ID No.: ____________ / Agent Code: <agentCode> / Time: <hh:mm> / Date: <date>` — the physical form's own "ID No./Agent-Code/Time/Date" print; there's no "ID No." concept anywhere in this system, so that segment is always blank for hand entry, while Agent Code/Time/Date are the document's real values.
- **Peso sign (₱) gotcha**: PDFKit's standard-14 fonts use WinAnsi encoding, which has no ₱ glyph — it silently renders as "±". See the font-choice note above for the fix (bundled DejaVu Serif, currency amounts only) and for why the obvious-looking alternative — embedding DejaVu Serif as the *body* font too, so there's only ever one font in play — was tried and reverted.
- **`pdf/assets/`** — `bethel-logo.png` (copied from `frontend/src/assets/`, so the backend has no dependency on the frontend build), `manager_signature.png`, and `fonts/DejaVuSerif(.ttf|-Bold.ttf)` (currency amounts only — see the font-choice note above; body text is PDFKit's standard-14 Times-Roman/Times-Bold, no font file to bundle for it).

### Middleware (`src/middleware/`)

- **`auth.js`** → `requireAuth`: reads `Authorization: Bearer <token>`, verifies JWT, sets `req.user = { userId, email }`.
- **`permissions.js`** → `requirePermission(code)` (Express middleware, 403 on missing), `requireAnyPermission(codes)` (Express middleware, passes once ANY code is held), `ensurePermission(res, codes, code)` (non-middleware helper for field-gated single routes — caller must `return` on `false`), `ensureAnyPermission(res, codes, [code, ...])` (same, for a field unlockable by more than one permission — e.g. `catalog.js`'s `PATCH /coverages/:id` `maximum_coverage` and `PATCH /product-variants/:id`'s rate fields, editable by either `MANAGE_SETTINGS.MANAGE_COVERAGE_PRICING` or `MANAGE_SETTINGS.MANAGE_PRODUCTS.EDIT_PRICING`), `getUserPermissionCodes(userId)` (unions role-granted + direct `UserPermission` grants; returns an **empty set** if `status` is `INACTIVE`/`SUSPENDED`, regardless of grants).
- **`validate.js`** → `validateBody`, `validateQuery`, `validateParams`: zod `safeParse` wrapper, 400s with `{ error: "<field>: <message>" }` (first issue only). `validateQuery`/`validateParams` use `Object.defineProperty` (not plain assignment) because Express 5 makes `req.query`/`req.params` read-only getters.

### Lib (`src/lib/`)

- **`agent.js`** → `getCurrentAgentId(userId)`: looks up `user.agent_id`. `getAccessibleAgentIds(agentId)`: returns `[agentId]`, or `[agentId, agent.company_id]` when this individual is employed under a `CORPORATE` agency — every `CompanyAgent`/ownership check that should also honor that agency's own `Agent.linked_company_id` link queries `agent_id: { in: accessibleAgentIds }` instead of a bare `agent_id: agentId` (see `routes/companies.js`'s `GET /`/`PATCH /:id` and `POST /policy-applications`/`POST /policy-quotations`'s own company-ownership checks).
- **`agentPerformance.js`** → `computeAgentPremiumTotals(prisma)`: every agent's own premium production — all-time and last-30-days — off `ApplicationCoverage.payable_to_bethel` (frozen at submission time, never recomputed off a later rate change). Factored out specifically because `routes/agents.js`'s own `GET /` (My Agents' premium columns) and `routes/accounting.js`'s `GET /overview` (the Accounting page's own agent-performance table) both need the exact same aggregation — one shared function so the two can never quietly drift apart.
- **`applicationEmails.js`** → `buildSubmissionEmailContent(detail)`/`buildApprovalEmailContent(detail)`: pure functions returning `{ subject, html, text }` for the two automatic `PolicyApplication` emails (see `send_policy_to_email`/`send_policy_to_email_on_approval` below) — kept as one shared lib, unlike the PDF builders in `src/pdf/` (which are deliberately duplicated per layout), because this is the exact same wording reused verbatim from three call sites (`POST /policy-applications`, `POST /policy-quotations/:id/submit`, `POST /policy-approval/:id/approve`), not a per-document layout that could ever need to diverge. Neither function sends anything itself — every call site builds its own PDF and calls `mailer.js`'s `sendMail()` directly, wrapped in a try/catch that logs and swallows a failure rather than failing the request that triggered it (the primary action — create, submit, or approve — has already succeeded by the time the email is attempted).
- **`endorsementEmails.js`** → `buildEndorsementSubmittedEmailContent({ insuredName, policyNumber, endorsementNumber })`/`buildEndorsementApprovedEmailContent({ insuredName, policyNumber, endorsementNumber, effectiveDate })`: the same shaped pair as `applicationEmails.js` below, for `routes/endorsements.js`'s own `send_policy_to_email`/`send_policy_to_email_on_approval` — kept as a separate file since it describes a different document (an amendment to an already-issued policy, not a new one), even though the shape is identical.
- **`coveragePricing.js`** → `round2`, `DOC_STAMPS_RATE`/`VAT_RATE`/`LGT_RATE` (also exported, pulled up from being locally duplicated in `policyApplications.js`/`policyQuotations.js`), `computeChargeTotals(rows, miscFee)` (the same `total_premium`/`doc_stamps`/`vat`/`lgt`/`misc` split those two routes each compute inline off a fresh `resolveCoverageRows()` result — pulled out here specifically for `routes/endorsements.js`'s `POST /:id/approve`, which has to recompute a `Policy`'s own charge totals from its *current* set of `PolicyCoverage` rows after an `ADD_COVERAGE`/`REMOVE_CLAUSE` line changes that set, not from a one-shot `resolveCoverageRows()` call; `rows` is anything carrying `{ premium_amount, is_misc }` — a `resolveCoverageRows()` row or a `PolicyCoverage` row alike), `resolveCoverageRows({ coverages, className, vehicles, vehicleValues, agentId, startAt, endAt })`: the shared pricing engine for applications+quotations (also called directly by `routes/endorsements.js`'s `priceAddCoverageChange()` to price an `ADD_COVERAGE` line — a single-coverage, single-vehicle-or-none call against the policy's own current period/agent). The `agentId` passed in is always the actual filing individual (never a company id) — the function itself resolves `effectiveAgentId = agent.company_id || agentId` once, up front, and every `AgentNetrate`/`AgentValuePercentageTier`/`AgentFlatTierPricing`/`AgentSeatsBasedPricing` lookup below reads through that instead, so an `INDIVIDUAL` agent linked to a `CORPORATE` one (see `Agent.company_id`) automatically prices off the company's own overrides — callers never need to resolve this themselves. Per coverage: confirms it's offered at the exact period (`endAt - startAt` must match an `allowable_periods.coverage_in_days`); resolves rate/tier by `pricing_mode` (agent override wins over product default, `VALUE_PERCENTAGE` uses depreciated vehicle value via a tax-bracket tier lookup, `FLAT_TIER` matches a fixed amount/price pair, `PERCENTAGE` validates against an effective max, `VEHICLE_SEATS_BASED` charges `rate_per_excess_seat` for every one of the targeted vehicle's own `no_of_seats` beyond `threshold_seats` — read straight off the `vehicles` array the caller already passed in, no extra DB lookup needed — and 400s if that mode is targeted at no vehicle at all, e.g. a Property application); **floor enforcement**: agent-entered `premium_amount` can never be below computed `payable_to_bethel` (throws `HttpError(400)` otherwise). Every resolved row also carries `is_misc`, read straight off the `ProductCoverage` row (`coverageDetails` select) — the pricing mode branches don't otherwise care about it; it's purely there for the caller (`routes/policyApplications.js`/`routes/policyQuotations.js`) to split `total_premium` vs. `misc` by.
- **`httpError.js`** → `HttpError` (carries `status`+`body`), `sendIfHttpError(err, res)` (writes the response and returns `true` if `err instanceof HttpError`, else `false` so the route's `next(err)` still runs) — lets deep helpers throw typed HTTP errors without threading `res` through.
- **`mailer.js`** → `sendMail({ to, subject, html, text, attachments })`: lazy-cached `nodemailer` transport from `SMTP_HOST/PORT/USER/PASS/FROM` env vars; throws `HttpError(503, ...)` if unconfigured rather than crashing the server at boot. Sets an explicit `name` (EHLO hostname) from the sending domain — without it, nodemailer can't determine a real hostname inside Docker's network namespace and identifies itself as `EHLO [127.0.0.1]`, which mail servers treat as a spam signal and silently accept-then-never-deliver (no bounce). Used by quotation resend, by `auth.js`'s forgot-password and `users.js`'s invite/re-verification flows (the latter two always log the link too and never let a send failure change their response/fail the request, since a link stays reachable manually as a fallback — and forgot-password's anti-enumeration response has to stay identical either way), and by the two automatic `PolicyApplication` emails built via `applicationEmails.js` (`POST /policy-applications`, `POST /policy-quotations/:id/submit`, `POST /policy-approval/:id/approve` — see those routes' own entries and `PolicyApplication.send_policy_to_email`/`send_policy_to_email_on_approval` below).
- **`policyConflicts.js`** → `resolveVehicleRenewal(vehicleIds, coverageStartAt, coverageEndAt, { enforce = true, excludeApplicationId = null })`, `resolveRiskAddressRenewal(addressId, coverageStartAt, coverageEndAt, { enforce = true, excludeApplicationId = null })`: the "no double-insuring the same asset" rule, extended to also auto-detect renewal continuity — global (not scoped to the caller's own agent or party), since a specific vehicle/risk address can only validly be covered by one policy at a time regardless of who's now applying for it, and regardless of which agent issued its prior history (a vehicle's policy trail follows the *asset*, not the agent — see `CustomerAgent`/`CompanyAgent` below on why two different agents can each have the same customer on file yet only ever see the policies they themselves issued). Two conditions, both keyed on vehicle (Motor, one call per application/quotation's whole vehicle list) or `RISK`-role address (Property):
  1. **Unconditional block** (thrown whenever `enforce: true`, regardless of dates): a `PolicyApplication` for the same vehicle/address still pending approval (`status` in `DRAFT/SUBMITTED/FOR_EDIT_*/PENDING_*_APPROVAL` — `REJECTED` doesn't count, it freed up whatever it referenced; `APPROVED` doesn't count either, since condition 2 governs from then on). No renewal path out of this one — an unresolved pending application has no known final dates to renew from. `excludeApplicationId` (passed by `routes/policyApproval.js`'s `POST /:id/approve`, which re-runs this same check at approval time) excludes one specific application's own id from this query — without it, an application being approved would flag itself as its own "pending application" conflict, since it's still in a pre-`APPROVED` status at the moment that route's check runs.
  2. **The single most-recently-issued `Policy`** already on file for that vehicle/address (if any), regardless of status. When `enforce: true`, an `ACTIVE` policy whose `expiry_date` is still after the new `coverage_start_at` blocks outright (`HttpError(409)` with a structured `conflict: { policy_id, policy_number, expiry_date }` body alongside the message — lets a caller offer a direct "renew this policy" action rather than a dead end); one that's already `EXPIRED`/`CANCELLED`/`LAPSED` never blocks. Either way, the result carries `{ renewedPolicyId }` — the found policy's id, so the caller can auto-set `policy_type: RENEWAL`/`renewed_policy_id` even when the agent never explicitly asked for a renewal. **Under no circumstance is an application/quotation left as `NEW_POLICY` once at least one vehicle on it has any policy history at all**: for a multi-vehicle Motor application where different vehicles disagree on which policy they'd each continue, the most recently issued one (by `effective_date`) wins as the link rather than the ambiguity being discarded — each vehicle's own active-policy date rule above still applies independently regardless of which one was picked as the link.
  `enforce: false` (only `POST /policy-quotations`'s own creation, and its `PATCH /:id`) skips both blocking conditions entirely and just computes `renewedPolicyId` — a quotation is a non-binding preview, so this is recorded silently; the real enforcement happens fresh at `POST /:id/submit`, never trusting what the quotation stored (real-world state may have changed since).
  **Known accepted gap**: only ever catches a vehicle/address match when the agent actually reuses the same on-file `Vehicle`/`Address` row. Vehicle plate collisions are additionally guarded at the row-creation layer (see `POST /policy-applications`/`POST /policy-quotations`'s own plate-uniqueness pre-check, and `PATCH /vehicles/:id`'s same check when a plate is edited) since `Vehicle.plate_number` carries no DB-level uniqueness — but `Address` has no natural key at all and no equivalent lookup/reuse-forcing flow, so a re-typed "new" risk address for the same physical property is invisible to this check.
- **`priorityPagination.js`** → `fetchByPriority({ delegate, pendingWhere, decidedWhere, pendingOrderBy, decidedOrderBy, select, skip, take })`: fetches one page out of a two-bucket priority list — a pending row always outranks a decided one, regardless of either bucket's own ordering — without loading the whole table into memory. Counts the pending bucket, then issues one or two `findMany()` calls (pending first, decided only if the page reaches past it) with skip/take arithmetic that treats the two buckets as one virtually-concatenated list, the same result a single `UNION ALL` with a priority column would give, without raw SQL. Used by `routes/policyApproval.js`'s `GET /` (Policy Approval) and `routes/endorsements.js`'s `GET /` (Endorsement Approval) — see those routes' own entries.
- **`prisma.js`** → singleton `PrismaClient` via `PrismaPg` adapter; client generated to `backend/generated/prisma` (custom output path).
- **`vehicleValue.js`** → `currentVehicleValue(estimatedValue, initialAssessmentDate, asOf)`: `estimatedValue * (1 - 0.1)^wholeYearsElapsed` (`ANNUAL_DEPRECIATION_RATE = 0.1`, anniversary-exact year counting); `findApplicableValueTier(tiers, value)`: highest `min_value` ≤ value. Mirrored client-side (non-authoritative) in `frontend/src/utils/vehicleValue.js`.

batch or a policy cancellation (exactly one `CANCEL_POLICY` line, no others) — see `EndorsementRequest.request_type` below, `EndorsementChangeType`(POLICY_EFFECTIVE_DATE/INSURED_NAME_DETAILS/INSURED_ADDRESS_DETAILS/VEHICLE_MODEL/VEHICLE_MV_FILE/VEHICLE_PLATE_NO/VEHICLE_TYPE/VEHICLE_MAKE/VEHICLE_COLOR/VEHICLE_ENGINE_NO/VEHICLE_CHASSIS_NO/EDIT_CLAUSE/REMOVE_CLAUSE/ADD_COVERAGE/CANCEL_POLICY) — most values are still the same "corrections only" scope as `ApplicationChangeType` (`POLICY_EFFECTIVE_DATE` standing in for that enum's own `INSURED_FROM_DATE`, `EDIT_CLAUSE` the renamed-from-`ADD_CLAUSE` fine-print-only edit); three are financial — `ADD_COVERAGE` prices and, once approved, materializes a real `PolicyCoverage` row; `REMOVE_CLAUSE` (repurposed — no longer text-only) soft-deletes one; `CANCEL_POLICY` is the sole line on a `CANCELLATION` request — see `EndorsementChange` below and `routes/endorsements.js`'s own entry above, `AgentPayableTransactionType`(ISSUANCE/ENDORSEMENT/CANCELLED_POLICY/PAYMENT) — ISSUANCE always credits, PAYMENT always debits; ENDORSEMENT can now run either direction (`ADD_COVERAGE` credits, `REMOVE_CLAUSE` debits — the DB `CHECK` constraint was relaxed accordingly, see that migration); CANCELLED_POLICY always debits, created only by a `CANCEL_POLICY` endorsement's approval as a day-prorated refund — see `AgentPayableTransaction` below.

### The three parallel transactional entities — Quotation / Application / Policy

The core domain lifecycle. Each stage has its own fully independent child tables (never shared), so earlier-stage history stays immutable:

| Stage | Header (`*.prisma` file) | Vehicle join | Address join | Coverage line | Approval? | Payment info? |
|---|---|---|---|---|---|---|
| Quote | `PolicyQuotation` (quotations.prisma) | `PolicyQuotationVehicle` | `PolicyQuotationAddress` | `QuotationCoverage` | No | No |
| Application | `PolicyApplication` (applications.prisma) | `PolicyApplicationVehicle` | `PolicyApplicationAddress` | `ApplicationCoverage` | Yes (`ApprovalHistory`) | Yes (`payment_method`, `payment_remittance`, `bethel_payment_method_id`) |
| Issued policy | `Policy` (policies.prisma) | `PolicyVehicle` (+ snapshot fields) | `PolicyAddress` (+ snapshot field) | `PolicyCoverage` (+ snapshot fields) | Cancellation only (`CancellationHistory`) | N/A (settled at application stage) |

- **PolicyQuotation**: priced identically to an application (same coverage/pricing engine). Can be edited in place (`PATCH /policy-quotations/:id` — coverage period, `send_policy_to_email`, and coverages only; re-prices through the same `resolveCoverageRows` engine) and can be converted into a `PolicyApplication` (`POST /policy-quotations/:id/submit`) — see `PolicyApplication.source_quotation_id` below. Once converted, a quotation is frozen: both the edit and submit routes 409 on a quotation whose `converted_application` relation is already set. Fields: `id, insured_type, quotation_number (unique), customer_id?, company_id?, company_name_snapshot?, agent_id, agent_name_snapshot?, product_variant_id, coverage_start_at, coverage_end_at, quotation_date, total_premium, doc_stamps, vat, lgt, misc, send_policy_to_email, renewed_policy_id?, remarks?, created_at, updated_at`. Grand total (`total_premium+doc_stamps+vat+lgt+misc`) is never stored, always computed on read (see `toQuotationDetail()` in the route). `renewed_policy_id` (FK → `Policy`, relation `"QuotationRenewals"`) is auto-detected server-side (`lib/policyConflicts.js`, `enforce: false` — never client-supplied, never blocks) whenever a reused vehicle/risk address already has policy history, regardless of agent — unlike `PolicyApplication.policy_type`, there's **no visible "renewal" label anywhere on a quotation itself**; a quotation is a non-binding preview, so this stays a silent, best-effort hint that only becomes a real, enforced `policy_type: RENEWAL` once (and if) the quotation is actually submitted (`POST /:id/submit`, which re-resolves it fresh rather than trusting this stored value).
- **PolicyApplication**: adds `application_number (unique)`, `status: ApplicationStatus`, `application_date`, `submission_date`, `payment_method`, `payment_remittance`, `bethel_payment_method_id?` (FK → `AuthorizedPaymentMethod`, only set when remittance is `DIRECT_TO_BETHEL`), `document_folder_name?`, `source_quotation_id?` (FK → `PolicyQuotation`, `@unique` — set only when this application was created by converting a quotation rather than filed fresh; a given quotation can convert at most once), `send_policy_to_email` (emailed right after this application is filed/submitted — the "now under approval, please settle payment" notice, see `lib/applicationEmails.js`'s `buildSubmissionEmailContent`), `send_policy_to_email_on_approval` (emailed only once `POST /policy-approval/:id/approve` actually approves this application — the "your policy has been approved" notice with the issued `Policy`'s own PDF attached, see `buildApprovalEmailContent`; independent of the flag above — an agent can ask for either, both, or neither). `status` walks `DRAFT → SUBMITTED → FOR_EDIT_*/PENDING_*_APPROVAL → APPROVED/REJECTED`. `policy_type: ApplicationPolicyType` (`NEW_POLICY`/`RENEWAL`, `@default(NEW_POLICY)` at the DB level only so the migration adding it didn't fail on rows already on file) and `renewed_policy_id?` (FK → `Policy`, only set when `policy_type` is `RENEWAL`) are both always server-derived at `POST /policy-applications` from whether the client sent `renewed_policy_id` — see that route's own entry above and `routes/policies.js`'s `GET /:id/renewal-prefill`, which is what actually populates `renewed_policy_id` in the create payload from the Client Policies tab's "Renew This Policy" action. The Policy Applications tracker's own "Type" column (and Policy Approval's) reads this field directly.
- **Policy**: `application_id` is `@unique` — strict 1:1 child of exactly one application (created only once approved, via `POST /policy-approval/:id/approve`). `policy_status: PolicyStatus`, `issue_date/effective_date/expiry_date` are its own live-owned fields. In-lease tracking is no longer a flat boolean here — see `InLeaseBacklog` below for the table that replaced `added_to_inlease`/`inlease_added_at`. `coc_number`/`sa_number` (both optional `VarChar(50)`) are entered by the approver at the moment of approval (`POST /policy-approval/:id/approve`'s optional body) rather than collected anywhere earlier — a quotation/application never has either — and print on the issued policy PDF (`pdf/policyPdf.js`) as a second line right below "Policy No :"/"Date Issued:" respectively, whenever present. **`cancelled_at`** (nullable `Date`) is set once a `CANCEL_POLICY` endorsement is approved against this policy (`routes/endorsements.js`'s `POST /:id/approve`) — that endorsement's own `effective_date`, i.e. when the policy actually stopped being in force, not the approval timestamp; `policy_status` is what every read path actually branches on, this is just the "when" alongside it. **`total_premium`/`doc_stamps`/`vat`/`lgt`/`misc` are the one exception to "frozen at issuance forever" below** — an approved `ADD_COVERAGE`/`REMOVE_CLAUSE` endorsement recomputes and persists them off the policy's current (non-removed) `PolicyCoverage` set (see `PolicyCoverage`'s own entry below and `lib/coveragePricing.js`'s `computeChargeTotals()`), since those two change types are the one thing that can legitimately alter what a policy is actually charging. **Every other field a re-exported policy document would need is frozen at issuance as a `*_snapshot` column (or, for charges, plain owned columns) — nothing about the printed document is allowed to depend on a live FK that could still be edited afterward**, since (unlike a `PolicyQuotation`/`PolicyApplication`, which are still mid-flow) an issued `Policy` is otherwise the final, immutable stage:
  - `customer_name_snapshot`/`company_name_snapshot`/`agent_name_snapshot`/**`agent_code_snapshot`** (name *and* code, since only the name used to be frozen).
  - **`class_name_snapshot`/`variant_name_snapshot`** off `ProductVariant`/`InsuranceClass` — `product_variant_id` stays a live FK for reporting/joins, but a later rename must never change what an already-issued policy's PDF prints.
  - **`deductible_rate_snapshot`** off `ProductVariant.deductible_rate` — feeds the policy schedule's Section III Deductible/Authorized Repair Limit line (`pdf/theme.js`'s `computeDeductibleFigures()`/`TOWING_AMOUNT` — the repair limit is just this deductible plus a fixed ₱500 towing amount, no separate rate/snapshot); a later edit via Settings → Vehicle Rates must never change the figure on an already-issued policy's re-export.
  - **`renewed_policy_number_snapshot`** — frozen at approval time off the source `PolicyApplication`'s own `renewed_policy` relation (its `policy_number`, only when that application was filed/resolved as a `RENEWAL`). Feeds the "Renewing/Replacing:" line printed just above Period of Insurance on the policy schedule (see "PDF generation" below) — `null` for a `NEW_POLICY`. `PolicyApplication`/`PolicyQuotation` expose the equivalent live-joined `renewed_policy_number` on their own detail/preview-props mappings (`toApplicationDetail`/`toPreviewProps` in `routes/policyApplications.js`, `toQuotationDetail`/`toPreviewProps` in `routes/policyQuotations.js`) — only the issued `Policy` freezes it, matching the snapshot pattern every other printed field here follows.
  - **`total_premium`/`doc_stamps`/`vat`/`lgt`/`misc`/`remarks`** — copied verbatim from `PolicyApplication` at issuance, never recomputed from the `DOC_STAMPS_RATE`/`VAT_RATE`/`LGT_RATE` constants again afterward (those constants could themselves change in a future code deploy; a `Policy`'s own charges must not move if they do). Grand total is still never stored, computed on read the same way as the other two stages.
  - **`PolicyVehicle`**: `vehicle_id` stays a live FK (ownership/depreciation still need it), but `plate_number_snapshot`/`mv_file_no_snapshot`/`engine_number_snapshot`/`chassis_number_snapshot`/`make_snapshot`/`model_snapshot`/`year_model_snapshot`/`vehicle_type_snapshot`/`color_snapshot`/`no_of_seats_snapshot` are frozen off `Vehicle` at issuance — necessary because a `PolicyApplicationChange`'s `VEHICLE_*` corrections write straight onto the *shared* `Vehicle` row (see `PolicyApplicationChange` below), so without a snapshot a correction logged against a later, unrelated application for the same repeat customer's vehicle would silently rewrite what an already-issued policy's PDF shows.
  - **`PolicyAddress`**: `address_id` stays a live FK, but `formatted_address_snapshot` (the same comma-joined shape `formatAddress()` in `routes/policyApplications.js` already produces) is frozen at issuance — `Address` rows have no freeze rule at all and are always editable via `PATCH /addresses/:id`.
  - **`PolicyCoverage`** additionally freezes `coverage_code_snapshot`/`coverage_name_snapshot`/`clause_snapshot`/**`pricing_mode_snapshot`** off `ProductCoverage` at issuance (catalog can change later, issued wording — and, now, which policy-schedule section a coverage prints under — must not) — `clause_snapshot` takes any `ADD_CLAUSE`/`REMOVE_CLAUSE` change recorded for that coverage line over the catalog's own `clause` text, and `effective_date` takes an `INSURED_FROM_DATE` change over `PolicyApplication.coverage_start_at`, if either was recorded (see `PolicyApplicationChange` below) — when it is, `expiry_date` shifts by the same amount off `PolicyApplication.coverage_end_at` rather than staying put, so the issued policy's period keeps its originally-quoted length instead of silently shrinking/stretching. Also carries, added for the endorsement engine (see `routes/endorsements.js`'s own entry above): `payable_to_bethel?`/`applied_rate?` (the row's own margin/rate — null on any row created before these columns existed, since issuance never used to persist them; `is_misc_snapshot` (frozen off `ProductCoverage.is_misc` at creation, `@default(false)`, backfilled from the live catalog value in that same migration) — both needed so a later `ADD_COVERAGE`/`REMOVE_CLAUSE` endorsement can compute its own `AgentPayableTransaction` margin and recompute the policy's charge totals without a live re-price; `policy_vehicle_id?` (only ever set on a row created by `ADD_COVERAGE` — which of the policy's own vehicles it was priced against; an issuance-time row never sets this, since `PolicyCoverage` rows don't retain a vehicle scope — see `GET /policies/:id/renewal-prefill`'s own note); `added_by_endorsement_id?`/`removed_at?`/`removed_by_endorsement_id?` (audit pointers, not Prisma relations — `removed_at` non-null means this line no longer counts toward the policy's current coverages/charges; every read filters it via `WHERE removed_at IS NULL`, see `routes/policies.js`'s `policyDetailSelect`).
  - All of the above are populated in `routes/policyApproval.js`'s `POST /:id/approve` from data fetched fresh at approval time (so any `VEHICLE_*`/`INSURED_ADDRESS_DETAILS` correction already applied to the underlying row by then is naturally captured too — "as of approval" includes every correction recorded before approval happened) and built once into local variables (`vehiclesForPdf`, `coveragesForPdf`, `insuredAddressSnapshot`) shared by both the snapshot-row inserts and the approval-notification email's own PDF attachment, so the two can never disagree with each other. There's no client input to any of this — every new field is server-computed from already-validated upstream data, so no zod schema changes were needed for the approve route itself (it still takes no body).
- **InLeaseBacklog**: replaces the old flat `Policy.added_to_inlease`/`inlease_added_at` booleans with one row per required in-lease task, so a policy can carry more than one over time instead of a single yes/no. Fields: `id, policy_id (FK), type: InLeaseTaskType, endorsement_request_id? (FK → EndorsementRequest), accomplished_by_user_id? (FK → User), accomplished_at?, created_at, updated_at`. Created by `POST /policy-approval/:id/approve` (`type: "FOR_UPLOAD"`, `endorsement_request_id: null`, unaccomplished) at policy issuance — see that route's own entry above — and by `routes/endorsements.js`'s own `POST /:id/approve` (`type: "FOR_ENDORSEMENT"`, `endorsement_request_id` set to that specific request, unaccomplished) once an endorsement against the policy is approved. `endorsement_request_id` is what lets `routes/inLeaseBacklog.js`'s `GET /:id` resolve which endorsement's own changes to show in copyable format once a `FOR_ENDORSEMENT` row becomes the policy's current task — it's otherwise `null` on a `FOR_UPLOAD` row. A row starts unaccomplished and is marked done via `routes/inLeaseBacklog.js`'s `POST /:id/accomplish` (sets both `accomplished_*` fields to the acting user/now) or reverted via `POST /:id/undo` (clears both back to `null`) — a policy's own in-lease status is never stored directly, always derived as "every row accomplished" (`ACCOMPLISHED`) vs. "at least one isn't" (`PENDING`, surfacing whichever unaccomplished row is oldest by `created_at` as the current task).
- Coverage line rows (`ApplicationCoverage`/`QuotationCoverage`) share the shape `coverage_amount, premium_amount, payable_to_bethel, applied_rate, {application|quotation}_vehicle_id?` (null = applies to all vehicles on that record) — `applied_rate` freezes the agent's net rate at submission time so historical branch revenue stays accurate even if rates change later; `premium_amount - payable_to_bethel` = the agent's profit on that row.
- **AgentPayableTransaction** (`agentPayables.prisma`) — an agent's running payable ledger: one signed-amount table rather than a separate "amount owed" table and "payments" table, the standard accounts-payable pattern (an agent's current balance is always just `SUM(amount) WHERE agent_id = ...`, mirrored for read efficiency onto `Agent.payable` — see that column's own entry below — and the full history reads chronologically off one table). Fields: `id, agent_id (FK), transaction_type: AgentPayableTransactionType, amount (signed Decimal), policy_id? (FK → Policy), endorsement_request_id? (FK → EndorsementRequest), remarks?, created_by_user_id? (FK → User), created_at`. Append-only, same "never edited in place" contract as `ApprovalHistory`/`CancellationHistory` — correct a mistake with an offsetting entry, not a mutation. `transaction_type` has four values: `ISSUANCE` always credits (`amount >= 0`), `PAYMENT` always debits (`amount <= 0`), `CANCELLED_POLICY` always debits (`amount <= 0`); `ENDORSEMENT` can run **either** direction — enforced by a hand-written DB `CHECK` constraint (`AgentPayableTransaction_amount_sign_check`, added by raw SQL in its own migration since Prisma has no `@@check` schema syntax, then relaxed in a later migration once `ENDORSEMENT` needed both signs) that catches every writer, present or future. `POST /policy-approval/:id/approve` creates one `ISSUANCE` row per approval (`policy_id` set to the just-issued `Policy`, `amount` = `SUM(premium_amount - payable_to_bethel)` across that application's own `ApplicationCoverage` rows — the agent's total margin on the sale, computed and credited even when it's exactly `0`, so the ledger's own row-per-policy history stays complete) and increments `Agent.payable` by the same amount, in the same transaction. `routes/accounting.js`'s `POST /payments` creates `PAYMENT` rows (see that route's own entry below). `ENDORSEMENT` and `CANCELLED_POLICY` are both created by `routes/endorsements.js`'s `POST /:id/approve` now: `ENDORSEMENT` positive when an `ADD_COVERAGE` line materializes its own `PolicyCoverage` row (credited with that row's own margin), `ENDORSEMENT` negative when a `REMOVE_CLAUSE` line soft-deletes one (debited by the removed row's own margin — falling back to treating the whole `premium_amount` as margin for a legacy `PolicyCoverage` row with no recorded `payable_to_bethel`); `CANCELLED_POLICY` (always negative) when a `CANCEL_POLICY` endorsement is approved — a day-prorated refund of the commission already earned on that policy (`computeCancellationProration()`, off `SUM(ISSUANCE + ENDORSEMENT)` for that `policy_id`, the policy's current effective/expiry dates, and the cancellation's own `effective_date`), with the full days-used/days-remaining/daily-rate breakdown written into `remarks` for auditability.
- **`Agent.payable`** (`parties.prisma`) — a denormalized running total of that agent's own `AgentPayableTransaction.amount` sum, kept in sync by every write to that table (`POST /policy-approval/:id/approve`'s `ISSUANCE` credit, `routes/endorsements.js`'s `POST /:id/approve` `ENDORSEMENT`/`CANCELLED_POLICY` credits/debits, `POST /accounting/payments`'s `PAYMENT` debit) via Prisma's atomic `{ increment/decrement: ... }`, never read-then-written. Exists purely so the Accounting Overview page can list every agent's current balance in one unpaginated query instead of a `GROUP BY` over the whole ledger on every page load — the ledger table itself stays the actual source of truth for auditing (`GET /accounting/transactions`), this column is a cache.
- **PolicyApplicationChange** (applications.prisma): an approver's audit trail of corrections against one `PolicyApplication`, recorded via `POST /policy-approval/:id/changes` without the `PolicyApplication` row itself ever being touched — see `routes/policyApproval.js` above. Fields: `policy_application_id (FK), application_vehicle_id? (FK → PolicyApplicationVehicle — which of the application's vehicles, for a Motor application with more than one), application_coverage_id? (FK → ApplicationCoverage — which coverage line, for AddClause/RemoveClause), change_type: ApplicationChangeType, change_from?, change_to?, effective_date?, remarks?, created_by_user_id (FK → User), created_at`. `change_from`/`change_to` are always computed server-side, never trusted from the client. For `VEHICLE_*` (all 8 individual `Vehicle` columns — model/mv_file_no/plate_number/vehicle_type/make/color/engine_number/chassis_number) and `INSURED_ADDRESS_DETAILS` (every column of the application's `INSURED`-role `Address` — `address_line_1`/`address_line_2`/`barangay`/`city`/`province`/`postal_code`/`country`, submitted as `new_address` rather than `new_value` — see `createApplicationChangeSchema` above), the new value is *also* written straight onto the underlying `Vehicle`/`Address` row (`change_to` itself stays the human-readable combined string, via `formatAddress()`), so the correction is already there the next time that same vehicle/address is selected on a future application/quotation — the catalog record changes permanently, not just this one application's picture of it. `ADD_CLAUSE`/`REMOVE_CLAUSE` instead amend a copy of the coverage's clause text scoped to `change_to` on this one change row — the shared `ProductCoverage.clause` catalog entry is never touched (that would silently reword every other application/quotation using that coverage too). `INSURED_FROM_DATE`/`INSURED_NAME_DETAILS` have no backing catalog record at all — logged only. Every change type's correction is folded back in wherever this application's own detail/PDF is re-rendered (`applyChangesToDetail()` in `routes/policyApplications.js`, see above) and, for `INSURED_FROM_DATE`/`INSURED_NAME_DETAILS`/clause changes specifically, into the issued `Policy` on approval (see above) — `VEHICLE_*`/`INSURED_ADDRESS_DETAILS` changes need no such folding-in anywhere, since every read of `Vehicle`/`Address` already sees the corrected row.

### Endorsements against an issued Policy (`endorsements.prisma`)

A fourth transactional entity, layered *on top of* an already-issued `Policy` rather than alongside quote/application/policy — an insurance endorsement, filed by the agent from the Client Policies page and reviewed/decided by an approver on the Approvals page's "Endorsement Approval" tab (`routes/endorsements.js`, see its own entry above).

- **EndorsementRequest**: the header row an agent files. Fields: `id, policy_id (FK), endorsement_number (unique, "<policy_number>-E<sequence_no>"), sequence_no (unique per policy_id), status: EndorsementStatus, request_type: EndorsementRequestType (@default(CORRECTION)), effective_date, remarks?, send_policy_to_email, send_policy_to_email_on_approval, created_by_agent_id (FK → Agent), created_by_user_id (FK → User), created_at, updated_at`. `effective_date` is when *this* amendment (or, for a `CANCELLATION`, the cancellation itself) takes effect — for a `CORRECTION` the endorsement template's own "...and expires..." half is never stored anywhere, always read live off the policy's own (possibly already-shifted-by-an-earlier-endorsement) `expiry_date` at render time. `status` walks `SUBMITTED → APPROVED/REJECTED`, terminal either way, same shape as `ApplicationStatus`'s own `APPROVED`/`REJECTED` pair. A `CORRECTION` still never writes onto the `Policy` row (or its `PolicyVehicle`/`PolicyAddress` children) it amends, even once `APPROVED` — every later read of that policy folds its approved corrections back in at read time instead (see `routes/policies.js`'s `applyEndorsementsToPolicyDetail()`, above). A `CANCELLATION`, and a `CORRECTION` carrying an `ADD_COVERAGE`/`REMOVE_CLAUSE` line, are the exceptions — see `EndorsementChange`'s own entry below and `routes/endorsements.js`'s `POST /:id/approve`.
- **EndorsementChange**: one amendment line within an `EndorsementRequest` — same `change_from`/`change_to`-computed-server-side contract as `PolicyApplicationChange`, just addressed at a `Policy`'s own `PolicyVehicle`/`PolicyCoverage` (`policy_vehicle_id?`/`policy_coverage_id?`) instead of an application's, via `EndorsementChangeType`. Unlike `PolicyApplicationChange` (approver-only, added one at a time after the fact), an agent files a whole batch of these together in one `POST /endorsements` — an approver can then add to/edit/remove from that batch (`POST`/`PATCH`/`DELETE /endorsements/:id/changes/...`) while the request is still `SUBMITTED` (a `CANCELLATION`'s own single `CANCEL_POLICY` line is the one exception — never addable/editable/removable there), the same edit capability `PolicyApplicationChange` already gives an approver over an application, just now also reachable on the agent's own initial submission. `VEHICLE_*`/`EDIT_CLAUSE` never write onto the shared `Vehicle`/`ProductCoverage` catalog rows the way `PolicyApplicationChange` does — there's no live row to correct here at all; the "current value" a new line diffs against is always this policy's own state as already amended by every earlier *approved* endorsement (`foldEndorsementChanges()`), never a shared catalog record another filing could also be reading. Extra columns, populated only for the two coverage-financial change types (null otherwise) — see `EndorsementChangeType`'s own comment for what each one does once approved:
  - `product_coverage_id` (FK → `ProductCoverage`, `ADD_COVERAGE` only) — which catalog coverage to add.
  - `coverage_amount`/`premium_amount`/`payable_to_bethel`/`applied_rate`/`is_misc` — the full `lib/coveragePricing.js`-resolved row, frozen at filing time (same "applied_rate freezes at submission" convention as `ApplicationCoverage`/`QuotationCoverage`) for `ADD_COVERAGE`; for `REMOVE_CLAUSE`, a frozen copy of the *removed* `PolicyCoverage`'s own values at filing time, decoupled from a live re-read at approval.
  - `created_policy_coverage_id` — set only after approval, once `ADD_COVERAGE` actually materializes its own `PolicyCoverage` row (an audit pointer, not a Prisma relation).
- **EndorsementApprovalHistory**: append-only decision log, same shape as `ApprovalHistory`, kept as its own table rather than widening that one's `policy_application_id`-shaped FK to mean two things.
- **PDF**: `pdf/endorsementPdf.js` renders the endorsement letter template (letterhead → header block → "effective...expires..." line → numbered plain-English amendment narrative → fixed legal boilerplate → signature block) — see the PDF generation section above. The charges block is no longer a hardcoded `0` — `computeEndorsementChargeDelta()` (routes/endorsements.js) sums the pricing *change* this endorsement's own `ADD_COVERAGE`/`REMOVE_CLAUSE` lines introduce. Once `APPROVED`, the same page is also appended directly into the base `Policy`'s own PDF (`pdf/policyPdf.js`), right after the main schedule, in the same file — the `Policy` row/snapshot columns stay exactly as issued, but any future export of it carries the endorsement's own page (and, for a financial one, the policy's own now-updated charge totals via the main schedule itself).

### Party model (`parties.prisma`, `locations.prisma`)

- `Customer`/`Company` are both "insureds" (`InsuredType` on quotes/applications says which). `Customer.company_id` optionally links a customer to a company. `Agent` is required (non-null `agent_id`) on every quote/application/policy.
- **`Agent.agent_type`/`Agent.company_id`** — an agent is either `INDIVIDUAL` (an actual person, the only kind that can hold a `User` login — see `access.prisma`'s own `User.agent_id` note below) or `CORPORATE` (an agency/company, no login of its own). `company_id` is a **self-referential** FK (`Agent.id → Agent.id`, mirroring `Customer.company_id → Company.id`'s own shape) — only ever set on an `INDIVIDUAL` agent, naming which `CORPORATE` agent they're currently an employee of, if any; a `CORPORATE` agent can never itself have one (single level, no chains). It's freely mutable (join or leave a company any time) and purely a pricing-resolution pointer — `lib/coveragePricing.js`'s `resolveCoverageRows` and `routes/agents.js`'s rate-management routes resolve every `AgentNetrate`/`AgentValuePercentageTier`/`AgentFlatTierPricing` lookup through `agent.company_id ?? agent.id` instead of the individual's own (now-dormant, never-deleted) override rows — but a `Policy`/`PolicyApplication`/`PolicyQuotation`'s own `agent_id` is **never** rewritten to the company: it always stays the specific individual who actually filed it, so per-employee attribution, `CustomerAgent`/`CompanyAgent` client-assignment, and premium-production figures all stay meaningful even once that employee joins a company. Agents are only ever created via `POST /agents` (the My Agents page's "Add Agent"/"Add Company" action) — `routes/users.js` no longer creates one inline when registering a user; it only links to one already on file.
- **`Agent.linked_company_id`** — wholly separate from `company_id` above: only meaningful (and only ever set) on a `CORPORATE` agent, this is a real FK to the insured-party `Company` table (`companies.prisma`), letting an agency also be filed for as a client. Set at creation (`POST /agents`'s `linked_company_id`/`new_company`, mutually exclusive) alongside a `CompanyAgent` link keyed to that `CORPORATE` agent's own id — since a `CORPORATE` agent never logs in to use that link directly, `lib/agent.js`'s `getAccessibleAgentIds()` is what actually surfaces it to every `INDIVIDUAL` employed under the agency (`Agent.company_id` pointing back at it), via `routes/companies.js`'s `GET /`/`PATCH /:id` and the company-ownership check in `POST /policy-applications`/`POST /policy-quotations`.
- `PartyAddress`/`PartyVehicle` (locations.prisma) are unified join tables — `customer_id`/`company_id` both optional but mutually exclusive (one party, never both), explicitly documented as a merge of what used to be separate `Customer*`/`Company*` join tables so ownership queries run as a single OR.
- `CustomerAgent`/`CompanyAgent` are the many-to-many assignment tables gating which parties an agent may quote/apply/edit for (checked on every relevant write route).
- `Address`/`Vehicle` are party-agnostic catalog records; `Vehicle.initial_assessment_date` is stamped automatically the first time `estimated_value` is ever set, then frozen — see "freeze rule" above. `Vehicle.no_of_seats` (required `Int`, `@default(5)` at the DB level only so the migration adding it didn't fail on rows already on file — every application-level create/edit always supplies a real value) feeds the policy schedule's driver/occupants endorsement line, not the freeze rule. **`Vehicle.product_variant_id`** (nullable FK → `ProductVariant`, Motor-only — enforced at the application layer in `routes/policyApplications.js`/`policyQuotations.js`/`vehicles.js`, not a DB constraint, same as this app's other cross-table invariants) — which Motor sub-product (e.g. "Private Car" vs. "Commercial Vehicle") this vehicle is currently insured under. Unlike the freeze-on-first-assessment rule above, this is **freely mutable going forward** (`PATCH /vehicles/:id`'s `product_variant_id` is optional — omitted leaves it untouched, a real value re-points it) — e.g. a vehicle insured as Private Car one year can be corrected/switched to Commercial Vehicle on a later renewal; each already-issued `Policy`'s own `variant_name_snapshot` still freezes whichever variant actually applied to *that* policy, so changing a vehicle's current variant never rewrites history, only what a *future* filing defaults to. Required on every new vehicle create (`schemas/policyIntakeShared.js`'s `vehicleInputSchema`) and backfilled for existing rows from each vehicle's own most-recent Motor application/policy in the migration that added the column. Every vehicle on one Motor application/quotation must resolve to the same variant as the filing's own `product_variant_id` — checked server-side (400 on a mismatch), and surfaced in the wizard as a locked/conflict-aware inline field rather than a free per-vehicle choice (see "Shared application/quotation intake logic" below).

### Pricing catalog (`catalog.prisma`, agent overrides in `parties.prisma`)

Spine: `InsuranceClass → ProductVariant → ProductCoverage → CoverageAllowablePeriod`. `ProductVariant.deductible_rate` (nullable `Decimal`) is set via Settings → Vehicle Rates (`PATCH /product-variants/:id`) — the policy schedule's Section III Deductible/Authorized Repair Limit line (see "PDF generation" above) is computed off whichever `VALUE_PERCENTAGE` coverage's variant this belongs to (the repair limit itself is just that deductible plus a fixed ₱500 towing amount — `pdf/theme.js`'s `TOWING_AMOUNT` — there's no second rate); left `null` just omits both figures rather than computing off an assumed-0 rate. `ProductVariant.misc_fee` (nullable `Decimal`) is the flat "Miscellaneous" charge every application/quotation filed under this variant carries — no longer an amount the agent types in per filing; `POST /policy-applications`/`POST /policy-quotations` read it straight off the chosen variant, `null` treated as ₱0. `ProductCoverage.is_misc` (`Boolean`, default `false`) marks a *specific coverage* whose own resolved premium is folded into the Miscellaneous charge instead of the Premium total — set via Settings → Manage Products' Add/Edit Coverage dialogs (a checkbox next to coverage code/name, gated the same as those — `.ADD_COVERAGE`/`.EDIT_DETAILS`), validated with zod in `createProductCoverageSchema`/`updateCoverageSchema` (`schemas/catalog.js`). `lib/coveragePricing.js`'s `resolveCoverageRows()` reads it fresh per coverage and stamps it onto every resolved row; `POST /policy-applications`, `POST /policy-quotations`, and `PATCH /policy-quotations/:id` all split `resolvedRows` by this flag when computing charges — `total_premium` (the "Premium" line) sums only the non-`is_misc` rows, every `is_misc` row's premium is added to `misc` on top of `ProductVariant.misc_fee`, but statutory `doc_stamps`/`vat`/`lgt` are still computed off the *full* premium sum regardless (the flag only moves where a coverage's premium is displayed, never what it's taxed against). `ProductCoverage.pricing_mode: CoveragePricingMode` selects one of four parallel mode families, each keyed by `coverage_allowable_period_id` (never by coverage directly — a coverage can price differently per allowable period) with a **coverage-level default** and an optional **agent-level override** that fully replaces it:

| Mode | Coverage default table(s) | Agent override table(s) |
|---|---|---|
| `PERCENTAGE` | `CoveragePercentageBasedPricing` (1:1, `standard_rate`) | `AgentNetrate` (`netrate`, optional `maximum_coverage`) |
| `VALUE_PERCENTAGE` | `CoverageValuePercentageTier` (tax-bracket tiers: `min_value`+`rate_percentage`) | `AgentValuePercentageTier` (same shape) |
| `FLAT_TIER` | `CoverageTierBasedPricing` (`coverage_amount`+`coverage_price` pairs) | `AgentFlatTierPricing` (same shape) |
| `VEHICLE_SEATS_BASED` | `CoverageSeatsBasedPricing` (1:1, `threshold_seats` only) + `CoverageSeatsTierPricing` (tiers: `insured_amount_per_occupant`+`rate_per_excess_seat`) | `AgentSeatsBasedPricing` (`threshold_seats` only, 1:1 per agent+period) + `AgentSeatsTierPricing` (same tier shape) |

`VEHICLE_SEATS_BASED` prices a coverage off the targeted vehicle's own `Vehicle.no_of_seats` **and** an "Insured amount for each occupant" the agent picks from the coverage's own tier menu (`CoverageSeatsTierPricing`/`AgentSeatsTierPricing` — same "coverage picks a tier key, mirrored client-side" convention as `FLAT_TIER`, just paired with a per-tier rate instead of a per-tier fixed price): `coverage_amount` on the resulting line is `no_of_seats × insured_amount_per_occupant` (e.g. 15 seats at ₱100,000/occupant insures ₱1,500,000), and the premium floor is `(no_of_seats - threshold_seats) × that same tier's own rate_per_excess_seat` (e.g. a 7-seat threshold on that 15-seater floors at 8 × the ₱100,000 tier's own rate). `threshold_seats` itself is coverage-wide, not per-tier. Unlike `VALUE_PERCENTAGE`/`FLAT_TIER`, the agent still enters and can mark up `premium_amount` above this floor — same margin model as every other mode, not the "fully automatic, no margin" treatment `VALUE_PERCENTAGE` gets. See `lib/coveragePricing.js`'s own entry above.

### Access/audit (`access.prisma`, `history.prisma`)

- `User` optionally links to one `Agent` and/or one `Customer` (portal-style logins). RBAC: `Role`⟷`Permission` via `RolePermission`, plus direct `User`⟷`Permission` grants via `UserPermission` (independent of role), `User`⟷`Role` via `UserRole`.
- `Permission.permission_code` self-encodes hierarchy via dot-notation (`PARENT.CHILD`) rather than a separate grouping column — a code with no dot is a top-level page-access permission, a dotted one is scoped under that page.
- `ApprovalHistory` (per `PolicyApplication`) / `CancellationHistory` (per `Policy`) are append-only audit logs of every approver decision.

### Snapshot-field pattern

Many models carry `*_name_snapshot`/`*_snapshot` fields alongside the live FK (e.g. `PolicyApplication.company_name_snapshot`, `Policy.customer_name_snapshot`/`agent_name_snapshot`, `PolicyCoverage.coverage_code_snapshot`/`clause_snapshot`) — frozen display text as of that record's creation, so historical documents don't silently change if the referenced Company/Agent/Coverage is later edited.

### `payments.prisma`

`AuthorizedPaymentMethod` (`id, name (unique)`) — payment methods Bethel itself accepts when payment is remitted `DIRECT_TO_BETHEL` rather than collected by the agent first. Managed via Settings → Authorized Payment Methods.

### Permission-gating pattern

- `ProtectedRoute.jsx` — outer gate: no `token` → redirect `/login`.
- `RequirePermission.jsx` — inner gate: `permissions === null` (still loading) → render nothing; `permission` (a single code, or an array — holding ANY one is enough) missing entirely → redirect `/dashboard`; else render children. The array form exists for a page like `/approvals`, whose two tabs are each independently gated on their own permission, so the page itself has to admit a caller holding either one.
- `AuthContext.jsx` — on mount/token change calls `getMe(token)`, stores `permissions` (array of codes) + `agent`; `permissions: []` on failure.
- `nav/navItems.js` — each item has `permission: null | "CODE" | ["CODE", ...]` (same any-of array form as `RequirePermission`); `AppLayout` filters the sidebar the same way `RequirePermission` gates routes.
- Fine-grained in-page gating beyond page access uses the same `permissions` array directly, e.g. `MyAgents.jsx` conditionally shows premium/rate columns; `PolicyApplication.jsx` disables Submit without `CREATE_APPLICATION.AGENT_ISSUANCE` (form stays fillable); `Quotations.jsx` hides "New Quotation" without `QUOTATION_TRACKER.CREATE_QUOTATION`/`.ADMIN_CREATE_QUOTATION`, shows the table only with `QUOTATION_TRACKER.VIEW_QUOTATION`/`.ADMIN_VIEW_QUOTATION`, and adds an Agent column with `.ADMIN_VIEW_QUOTATION` specifically; `QuotationCreator.jsx` shows a cross-agent "Filing Agent" picker only with `QUOTATION_TRACKER.ADMIN_CREATE_QUOTATION`; `ManageProducts.jsx` hides each individual create/edit/delete affordance per tier behind its own `MANAGE_SETTINGS.MANAGE_PRODUCTS.*` sub-permission (see its own Pages entry below) — the most granular example of this pattern, since the whole page exists to let different catalog-management responsibilities be delegated to different people; `PolicyDetailDialog.jsx` hides "Create Endorsement Request" without `VIEW_POLICIES.CREATE_ENDORSEMENT`; `Approvals.jsx` shows only whichever of its two tabs (`APPROVE_APPLICATION`/`APPROVE_ENDORSEMENT`) the caller actually holds, rather than an empty tab they'd click through to a 403.

### API client contract (`src/api/client.js`)

`request(path, { method, body, token })` — sets `Content-Type`, `Authorization: Bearer <token>` if given, JSON-encodes body, throws `Error(data?.error || "Request failed with status <n>")` on non-2xx — that thrown `Error` also carries the full parsed body as `err.data` whenever the response was JSON, so a caller needing more than the message (e.g. `PolicyApplication.jsx` reading `err.data.conflict` off a vehicle/address double-insurance 409 — see `lib/policyConflicts.js`) doesn't need its own fetch. `requestBlob(path, { method, body, token })` is the same contract for the PDF endpoints, which return `application/pdf` instead of JSON — resolves to a `Blob` instead of parsed data.

### Pages (`src/pages/*.jsx`)

- **Login / ForgotPassword / SetPassword**: public auth flows; no client-side schema validation beyond HTML `required` + manual password-match check in `SetPassword`.
- **Dashboard**: fetches `getMe`, shows account info + status; warns if `INACTIVE`/`SUSPENDED`.
- **ManageUsers**: table of all users; `AddUserDialog`/`EditUserDialog` share a `RoleAndPermissionsFields` subcomponent and a second shared `AgentPickerField` (an `Autocomplete` over `listAgentsForUserLink`, `GET /users/agents`) — links a user to an already-existing agent rather than creating one inline (agents are only ever created via My Agents' own "Add Agent" now). **`AgentPickerField` is now a strictly-one-or-the-other `ToggleButtonGroup` ("Individual Agent" / "Company Agent") over the same `Autocomplete`** — switching modes clears the current selection and re-filters `agents` by `agent_type`: Individual keeps the original exclusivity behavior (an agent already linked to a *different* user, `has_user`, is left out of the list, except — on `EditUserDialog` — the one currently linked to the user being edited, `currentAgentId`, so editing without touching the agent field doesn't look empty); Company shows every `CORPORATE` agent regardless of `has_user` (many logins may share one) with `agentOptionLabel` showing `user_count` instead of a company suffix. `RoleAndPermissionsFields`'s own "Special permissions" list is now inside a collapsed-by-default MUI `Accordion` (starts open only when the user being edited already has some checked) — a long checklist of every sub-permission in the app was pushing the rest of the dialog out of view for the common case of no special grants at all. Shows a manually-shareable invite link after create/reverification since email isn't actually sent.
- **Settings**: pure navigation hub, no data fetching — links are grouped into three `Paper`/`List` sections ("Roles and Permissions", "Products and Pricing", "Payment Methods") via a `settingsGroups` array rather than one flat list; every link still renders regardless of the caller's permissions (the destination route's own `RequirePermission` is what actually gates it, same as before this grouping existed).
- **RoleDefaultPermissions / CreateRole**: dirty-tracking edit pages (current vs. original state, `isDirty` via `useMemo`, Save/Cancel only shown when dirty).
- **AuthorizedPaymentMethods**: simple add/delete list, client-sorted alphabetically.
- **ManageProducts** (`/settings/manage-products`, gated `MANAGE_SETTINGS.MANAGE_PRODUCTS` for page access only): the full `InsuranceClass → ProductVariant → ProductCoverage` catalog as one expanded tree (`GET /insurance-classes`, each coverage carrying its own `allowable_periods`), absorbing everything the three now-removed dedicated settings pages (`EditClauses`, `ManageCoveragePricing`, `ManageVehicleRates`) used to do — clause text, coverage pricing (via the embedded `components/CoveragePricingEditor.jsx`, see Components below), and variant rates are all edited from here now instead. Create actions and **exactly one "Edit" dialog per tier** (class/variant/coverage) rather than one dialog per field-group — every field inside that one dialog is independently shown or hidden based on the caller's own `permissions` array from `useAuth()` (`can.*` in the component), same fine-grained-in-page-gating precedent as `MyAgents.jsx`'s premium/rate columns, since this page's whole reason for existing is to let different sub-permissions be delegated to different people without needing different pages:
  - **Class row**: "Add Insurance Class" (top of page) needs `.ADD_CLASS`. The row's single "Edit" icon opens one dialog with `class_name`/`description` — its only field-group is `.EDIT_DETAILS`, so the dialog is either fully fillable or (rare) shows an "you don't have permission" notice instead of any field.
  - **Variant row**: the single "Edit" icon (shown whenever `.EDIT_DETAILS` OR `.EDIT_PRICING`/`MANAGE_COVERAGE_PRICING` is held) opens one dialog with two independently-gated groups separated by a `Divider` when both show — `variant_code`/`variant_name` under `.EDIT_DETAILS`, `deductible_rate` (same 0–1-fraction-stored/whole-percent-shown convention agent netrates use, via `rateToPercentDisplay`/`percentDisplayToRate`) under `.EDIT_PRICING` OR `MANAGE_SETTINGS.MANAGE_COVERAGE_PRICING` — one "Save" submits whichever groups are actually visible in a single `PATCH`. "Add Coverage" needs `.ADD_COVERAGE`.
  - **Coverage row**: allowable periods render as read-only `Chip`s (via `formatPeriodLabel`) directly on the row, each with a delete "x" (`can.editPricing`) plus an "Add period" chip that opens a small immediate-create dialog (`createAllowablePeriod`) — a lighter entry point than diving into the full Edit dialog just to add/drop one period. The row's single "Edit" icon (shown whenever `.EDIT_DETAILS`, `MANAGE_SETTINGS.EDIT_CLAUSES`, or `.EDIT_PRICING`/`MANAGE_COVERAGE_PRICING` is held) opens one dialog with three groups: `coverage_code`/`coverage_name` (`.EDIT_DETAILS`) and `clause` (the existing `MANAGE_SETTINGS.EDIT_CLAUSES` — reused as-is, not a Manage-Products-scoped permission) share a single "Save details" button since both `PATCH /coverages/:id`; below that, a "Pricing" section embeds `CoveragePricingEditor` (period/mode/rate/tiers/maximum coverage, `.EDIT_PRICING` OR `MANAGE_COVERAGE_PRICING`) with its **own** self-contained Save — kept separate rather than folded into "Save details" because it's a multi-step, period-scoped flow that doesn't collapse into one plain `PATCH` the way code/name/clause do.
  - **Deletion is staged, not immediate, across every tier including allowable periods** — clicking a delete icon (or a period chip's own delete "x") just toggles that id in/out of one of four `pendingDelete*Ids` `Set`s (`isClassPending`/`isVariantPending`/`isCoveragePending` fold cascade in: a variant under a pending class, or a coverage under a pending variant, shows as pending too even though its own id was never added — its own delete affordance is disabled, since undoing means un-marking the ancestor instead). A warning `Alert` appears once anything is pending, with "Discard" (clears every pending set, nothing was ever sent) and "Save Deletions" (`batchDeleteCatalogItems` → `PATCH /manage-products/batch-delete`, one request committing every marked id across every tier in a single transaction, then `loadClasses()`) — nothing is actually removed by a click alone. "Add"/"Edit" actions on a pending row are disabled while it's marked. Every other create/edit action (not delete) still calls `loadClasses()` immediately on its own success, same as before this staging existed.
- **MyAgents**: agent table (Type column — "Individual"/"Company" — plus, for an `INDIVIDUAL` linked to one, an "Under {company}" caption under its name) with permission-gated premium/rate columns; `RatesDialog` lets an admin set per-agent, per-coverage pricing overrides — net rate, a tier table, or — for `VEHICLE_SEATS_BASED` — both a seat-threshold field *and* its own tier list (insured amount per occupant + rate), saved as two independent overrides — depending on the coverage's mode. Reads `getAgentNetrates`'s `{ is_inherited, company_name, coverages }`, and once `is_inherited` is true (this agent is an `INDIVIDUAL` linked to a company) renders every checkbox/field disabled with an info `Alert` naming the company and only a "Close" action, since these rates are actually the company's own (see `lib/coveragePricing.js`) and have to be edited from that company's own row instead. "Add Agent" (gated `MANAGE_AGENTS.ADD_AGENT`) opens `AddAgentDialog` — an `agent_type` radio (Individual/Company), code/name/email fields; for Individual, an optional `Autocomplete` over the already-loaded agent list filtered to `agent_type: "CORPORATE"` (`company_id` on submit); for Company, an "Insured-party company record" radio — **"Select existing"/"Create new" only, no "None"** (a `CORPORATE` agent must always be company-backed now, matching `createAgentSchema`'s own refinement — see `routes/agents.js`'s `POST /` above; `companyLinkMode` defaults to `"existing"` rather than a since-removed `"none"`) — existing pulls from `listCompaniesForAgentLinking` (`GET /companies/for-agent-linking`), new collects the same fields `POST /companies` does (`company_code`/`company_name`/`tin_no`/email`) — sent as `linked_company_id`/`new_company` respectively. Whenever `agent_type` is `CORPORATE` (`isCompanyBacked`, now simply `agentType === "CORPORATE"` since every company agent is company-backed), the top Company name/Agent code/Work email fields switch to `disabled`, showing a "Taken from the company record below" `helperText`, and live-mirror whichever company is currently selected/being typed (`linkedCompany`/`newCompanyForm`) instead of their own independent state — `agent_code`/`agent_name`/`work_email` are omitted from the `createAgent` payload entirely in that case, since `POST /agents` derives all three off the `Company` record server-side regardless of what's sent (see that route's own entry above). This is the page's own "Add Agent"/"Add Company" action, and now the only place an `Agent` row gets created at all (see `routes/users.js`'s own note on no longer creating one inline).
- **Quotations** (Quotation Tracker, `/quotation-tracker`, gated on `QUOTATION_TRACKER`): server-paginated table (row data already carries `quotation_number`, so no JSON detail fetch is needed for the dialog title); **row click opens `QuotationDetailDialog`**, which fetches the actual PDF (`downloadQuotationPdf`) and renders it inline via `PdfViewer`. "Re-export PDF" reuses that same already-fetched blob URL (`window.open(pdfUrl, "_blank")` — no second request). "Resend to client" via `resendQuotationEmail`. "New Quotation" opens `QuotationCreator` embedded in a `Dialog` (not a separate route — see below); hidden without `QUOTATION_TRACKER.CREATE_QUOTATION` or `.ADMIN_CREATE_QUOTATION` (`canCreate`). The table itself renders only with `QUOTATION_TRACKER.VIEW_QUOTATION` or `.ADMIN_VIEW_QUOTATION` (`canView`) — an info `Alert` in its place otherwise, since `QUOTATION_TRACKER` alone (page access) doesn't imply either. With `ADMIN_VIEW_QUOTATION` specifically (`isAdminView`), an extra **Agent column** appears (`agent_name`/`agent_code`, mirroring `PolicyApproval.jsx`'s own) since the list then spans every agent, not just the caller's. A **Status column** (`QuotationStatus`, keyed off `row.status`, see `GET /policy-quotations` above) renders a short, fixed-width `Chip` per state — "Submitted" (plain), or, once converted, "For Issuance"/"Policy Issued" as a single clickable pill (`RouterLink` to `/policy-application?open=<converted_application_id>`, `onClick` calling `stopPropagation` so it doesn't also trigger the row's own detail dialog) — the resulting application/policy number moves into a `Tooltip` on the chip rather than being appended to its own label, since a generated number was stretching the column. **Class / Variant** is one combined column (class name over variant name, two-line stacked `Typography`) and **Coverage Period** collapses what used to be separate Insured-From/Insured-To columns into one `"<start> – <end>"` cell — both trims done specifically so this table reads less cluttered at its default width. An **Actions column** (edit/submit icon buttons, `stopPropagation`ed so they don't also trigger the row-click detail dialog) opens `EditQuotationDialog`/`SubmitQuotationDialog`; both disabled once `row.converted` is true (the quotation has already become a policy application) or without `canCreate` — Submit is additionally disabled without `CREATE_APPLICATION.AGENT_ISSUANCE` (`canIssue`).
- **EditQuotationDialog**: edits a saved quotation's coverage period, `send_policy_to_email`, and coverages (only what `PATCH /policy-quotations/:id` accepts) — fetches `getQuotation` + `getProductCatalog`, regroups the quotation's already-per-vehicle-expanded coverage rows back into one editable selection per coverage (via each row's `vehicle_index`, which `toQuotationDetail` on the backend derives from `policy_quotation_vehicle_id`), and runs its own copy of `resolveCoverageSelection` (mirrors QuotationCreator.jsx's, same non-authoritative-preview reasoning) since vehicles here are the quotation's fixed list, not user-entered ones. A datetime-local input round-tripping an *existing* UTC timestamp is the one thing genuinely new here (versus QuotationCreator.jsx, which only ever goes form → submit, never display-existing → resubmit): `toLocalDateTimeInput` deliberately reads UTC getters, not local ones, because the value gets sent back to the server as a naive string that `z.coerce.date()` parses in the *server's* timezone (UTC, no `TZ` set) — using local (browser) getters would silently shift the date by the browser/server offset the instant an unrelated field is edited and this one is simply resubmitted unchanged. Its `buildPreviewProps()` also passes through each coverage's `pricing_mode` and the quotation's own `deductible_rate` (already on `detail`, off the quotation's `product_variant`) — same PDF-section-split inputs QuotationCreator.jsx's own preview carries, see backend's "PDF generation" section. Like QuotationCreator.jsx, "Preview changes" is required before "Confirm and save" — fetches `previewQuotationPdf` into a nested preview `Dialog`; unlike QuotationCreator.jsx, "Preview changes" also stays disabled until the form actually diverges from an `initialSnapshot` captured right after load (`coverageStartAt`/`coveragePeriodDays`/`coverageSelections`/`sendPolicyToEmail`, deep-compared via a `useMemo` `isDirty`) — there's nothing to preview or save about an unedited quotation. The form is split into distinct sections matching QuotationCreator.jsx's own: "Coverage Period" (dates + period checkboxes), then "Coverages", then a "Charges" breakdown (Premium/Doc. Stamps/V.A.T./L.G.T./Miscellaneous/Total Php.) mirroring QuotationCreator.jsx's own Charges `Paper` (`misc` is still never sent by the client — `updateQuotationSchema` has no such field — but is no longer purely display-only server-side either: `PATCH /policy-quotations/:id` now recomputes and writes it, since a coverage's own `ProductCoverage.is_misc` flag can move its premium into this bucket on every re-price), then a "Delivery" section — deliberately last, below Charges, not grouped with Coverage Period — with a single checkbox, pre-checked by default regardless of the quotation's own stored value (every revision defaults to notifying the client of the change), labeled "Email this revised quotation to the client" (distinct wording from QuotationCreator.jsx's own "Send this quotation to the customer's email" — a revision notice, not a first delivery).
- **SubmitQuotationDialog**: converts a quotation into a policy application via `POST /policy-quotations/:id/submit` — collects the payment fields a quotation never asked for, plus two checkboxes for the application's two independent delivery flags (both pre-checked by default — unlike `PolicyApplication.jsx`'s own wizard, which leaves them unchecked for a fresh filing; converting an already-quoted deal defaults to notifying the client both times): "Email the customer now that the application is under approval (with payment instructions)" (`send_policy_to_email`) and "Email the customer their approved policy once this application is approved" (`send_policy_to_email_on_approval`) — neither is carried over from the quotation's own `send_policy_to_email`, since "email the client the quotation" and "email the client about the application it's about to become" are different decisions. Previews the resulting policy schedule (`previewApplicationPdf`, `isPreview: true`, application number shown as "TO BE ASSIGNED ON SUBMISSION") in a nested `Dialog`, and only then calls `submitQuotation`. Both this and EditQuotationDialog sanitize `null` DB fields (`vehicle.make`, etc.) to `""` before building preview props — `documentPreviewPropsSchema`'s vehicle fields are optional strings, which accept an omitted value but not an explicit `null`. Same checkbox-gated confirm as PolicyApplication.jsx's own preview dialog ("I have double-checked the information above and confirm it is correct." — Confirm and submit stays disabled until checked, reset every time the preview reopens) rather than a bare submit button — irreversibly converting a quotation deserves the same explicit double-check as filing a fresh application.
- **PolicyApplications** (Policy Applications tracker, `/policy-application`): same table/dialog shape as **Quotations** above — server-paginated table (`listApplications`) with a **Status column** (shared `components/StatusChip.jsx`, color keyed off `ApplicationStatus`). No Type column any more — the `policy_type` (`NEW_POLICY`/`RENEWAL`) chip and its filter dropdown were removed from this table (the field itself, and `PolicyApproval.jsx`'s own identical column/filter, are untouched — `policy_type` still drives `POST /policy-applications`'s own renewal logic, it's just not surfaced here). Same **Class / Variant** (stacked two-line cell) and **Coverage Period** (`"<start> – <end>"`) column merges as `Quotations.jsx`, plus a monospace `Application #` cell — same "streamline a wide tracker table" treatment applied consistently across it, `PolicyApproval.jsx`, and `ClientPoliciesTable` below. Row click opens the shared `components/ApplicationDetailDialog.jsx` (fetches the PDF via `downloadApplicationPdf`, renders via `PdfViewer`, "Re-export PDF"/`window.open` on the same blob, "Resend to client" via `resendApplicationEmail`); "New Application" opens `PolicyApplication` (the wizard, aliased on import as `PolicyApplicationCreator`) embedded in a `Dialog`. No Actions column — an application isn't edited or converted from here the way a quotation is. Also reads an `?open=<id>` query param on mount (via `useSearchParams`) — the Quotation Tracker's "For Issuance" link routes here with it, fetching that one application's detail (for the dialog title) and opening `ApplicationDetailDialog` straight away, then stripping the param back out of the URL (`replace: true`) so it doesn't re-trigger. A second, near-identical `?renew=<policyId>` param does the same for the Client Policies tab's "Renew This Policy" action — calls a shared `openRenewalPrefill(policyId)` function (fetches `getPolicyRenewalPrefill`, stores the result in `renewalPrefill` state, opens the "New Application" `Dialog`) then strips the param back out. That same `openRenewalPrefill` is also passed straight through to `PolicyApplicationCreator` as `onRenewalRequested` — its own way of reaching the identical flow from *inside* an already-open wizard (see that component's own `onRenewalRequested` entry above) without a round-trip through the URL. `PolicyApplicationCreator` is given `key={renewalPrefill?.renewed_policy_id || "new"}` specifically so either path forces a full remount rather than patching `renewalPrefill` onto a wizard instance that might already be mid-filled — a fresh instance can't end up with a stale mix of an abandoned attempt and the new prefill the way patching props onto a live one could. `renewalPrefill` is reset to `null` both when the create dialog is closed and when "New Application" is clicked manually, so a later fresh filing in the same session never accidentally inherits a stale renewal's date floor.
- **MyClients** (`/my-policies`, nav label "My Clients", gated `VIEW_POLICIES`): the route-level page — just a `Container`/heading plus a horizontal MUI `Tabs` bar ("Clients" / "Client Policies", plain local `useState` index, not URL-driven) switching between the two tab components below, which supply their own `Paper`/search-bar/table content without any page chrome of their own. Split out this way (rather than one page owning both) once the "Clients" tab was added, so each tab's own data-fetching/filtering stays independent.
- **Clients** (the "Clients" tab): every customer/company on file for the caller's own agent (`GET /policies/clients`), ranked by 30-day premium production — server-paginated table (search by name/email + a Type filter, same search/filter-bar convention as every other tracker), columns Name/Type/Email/Contact/Premiums (Last 30 Days)/Total Policies/Last Policy. `Contact` shows a customer's `mobile_number` or a company's `tin_no` (Company has no phone field). No row-click detail dialog — a client isn't itself a document the way a policy/application is; opening one is what the other tab is for.
- **ClientPoliciesTable** (the "Client Policies" tab, in `pages/ClientPolicies.jsx` — file name kept despite the export being renamed, since it still is that page's own table): an agent's own book of already-issued policies across all their clients, **closest-to-expire first** (see `routes/policies.js`'s `GET /` above — this table is as much a renewal worklist as a record of what's been issued) — server-paginated table (`listMyPolicies`, own-agent-only, same scoping as `PolicyApplications`), columns Policy #/Insured/**Class / Variant**/Status/**Coverage Period**/Total Premium/Issued/**Actions** (COC No./SA No. columns were removed — `coc_number`/`sa_number` are still on the row/PDF, just not surfaced in this table; Class/Product Variant and Effective/Expiry were each merged into one column, same streamlining as `PolicyApplications.jsx`/`PolicyApproval.jsx`). `Status` uses a small locally-defined `PolicyStatus` label/color map (`ACTIVE`/`EXPIRED`/`CANCELLED`/`LAPSED`) rather than the shared `StatusChip.jsx`, since that component is specifically `ApplicationStatus`'s mapping and `PolicyStatus` is a different enum with different values — same "duplicate a small local mapping" precedent as the two dialogs' own `CHANGE_TYPE_LABELS`. Row click opens `components/PolicyDetailDialog.jsx` — a two-pane dialog (the policy's own signed PDF on the left, policy info/endorsement history/"Create Endorsement Request" composer on the right, see that component's own entry below), not just a bare PDF viewer any more. The **Actions column** (`stopPropagation`ed so it doesn't also trigger the row's own detail dialog, same pattern as `Quotations.jsx`'s own Actions column) has two icon buttons: "Resend to client" (`resendPolicyEmail`, a top-level `Alert` rather than per-row feedback, since only one resend realistically runs at a time from this table) and "Renew This Policy" (`navigate` to `/policy-application?renew=<policyId>` — see `PolicyApplications.jsx`'s own `?renew=` handling and `PolicyApplication.jsx`'s `renewalPrefill` prop below). No create/edit affordance for a `Policy` itself here — one is only ever created via `POST /policy-approval/:id/approve`, never directly; "Renew This Policy" creates a new `PolicyApplication` (`policy_type: RENEWAL`), not a new `Policy`.
- **Approvals** (`/approvals`, gated on `[APPROVE_APPLICATION, APPROVE_ENDORSEMENT]` — either admits the page): a pure hub — `Container`/heading plus a horizontal `Tabs` bar switching between `PolicyApproval` and `EndorsementApproval` below (same "one page, two independently-supplied tab bodies" shape as `MyClients.jsx`'s own Clients/Client Policies split), except each tab here is *also* independently gated: `Approvals.jsx` reads the caller's own `permissions` and only lists the tab(s) they actually hold (`canApprovePolicies`/`canApproveEndorsements`), so a caller with just one of the two permissions sees a single, tab-bar-less page rather than a tab they'd click through to a 403. Renamed from the old standalone `/policy-approval` route/"Policy Approval" nav label once Endorsement Approval needed a home alongside it.
- **PolicyApproval** (no longer a standalone route — see **Approvals** above, same relationship as `PolicyApplication`/`PolicyApplications`): the cross-agent application approval queue — same streamlined table shape as PolicyApplications (Type column included), plus an **Agent column** (`agent_name`/`agent_code`); no Actions column. Backed by `listApplicationsForApproval` (`GET /policy-approval`, every application in the system, not just the caller's own, priority-sorted undecided-first — see that route's own entry). Row click opens `components/ApplicationReviewDialog.jsx` — one wide dialog with the PDF on the left and the change-history/"Create Change"/"Approve" panel on the right, side by side, rather than two separate popups (an older version opened `ApplicationDetailDialog` for the PDF and a dedicated Actions-column button for a separate `ApplicationApprovalDialog` — both replaced by this single dialog). `onApproved` calls `loadApplications()` again so an approval's status change shows up in the table immediately.
- **EndorsementApproval** (the "Endorsement Approval" tab of **Approvals** above): the cross-agent endorsement approval queue, same streamlined table/dialog shape as `PolicyApproval` — columns Endorsement #/Policy #/Agent/Insured/**Class / Variant**/Status/Effective/Filed (Class/Product Variant merged into one stacked cell, `Endorsement #`/`Policy #` set in monospace — same "streamline a wide tracker table" treatment as `PolicyApproval.jsx`/`PolicyApplications.jsx`/`Quotations.jsx`/`ClientPoliciesTable`, see the Shared UI conventions note below), backed by `listEndorsementsForApproval` (`GET /endorsements`, every request in the system). Row click opens `components/EndorsementReviewDialog.jsx`. `onDecided` calls `loadEndorsements()` again, same refresh-in-place pattern as `PolicyApproval`'s own `onApproved`.
- **Accounting** (`/accounting`, gated `MANAGE_ACCOUNTING`): pure hub page — `Container`/heading plus a horizontal `Tabs` bar switching between `AccountingOverview` (tab 0, the page's own default/first tab) and `AccountingTransactions` (tab 1), same "one page, two horizontal tabs, no per-tab permission filtering" shape as `MyClients.jsx`'s own Clients/Client Policies split (unlike `Approvals.jsx`, both tabs here share the one `MANAGE_ACCOUNTING` gate — only the "Record Payment" *action* inside Transactions has its own further permission, not the tab itself).
- **AccountingOverview** (the "Overview" tab): one row per agent — Agent (code `Chip` + name), Premiums Generated, Last 30 Days, Payable Balance — backed by `listAccountingOverview` (`GET /accounting/overview`). Unpaginated, same "small, complete roster" convention as `MyAgents.jsx`. `Payable Balance` reads `Agent.payable` directly (the denormalized running-total column — see that field's own Database entry) and renders in `warning.main` when positive (still owed to the agent) or plain `text.primary` otherwise; no row-click detail — this tab is a snapshot, not a document to open (the Transactions tab is where the underlying history is browsable).
- **AccountingTransactions** (the "Transactions" tab): the full `AgentPayableTransaction` audit log, cross-agent, newest first — same server-paginated, streamlined table shape as `PolicyApproval.jsx` (search + a Type `Select` — Issuance/Endorsement/Cancelled Policy/Payment — narrow the `where`; columns Date/Agent/Type (`Chip`, color keyed off `transaction_type` — green `ISSUANCE`, blue `ENDORSEMENT`, red `CANCELLED_POLICY`, default `PAYMENT`)/Policy # (monospace, "—" when null)/Amount (green `+₱X`/red `-₱X`, sign-colored via `amount < 0`)/Remarks (with a "by `<name>`" caption underneath when `created_by_name` is set)). No row-click dialog — each row is already a complete, immutable fact, nothing further to open. ### Shared UI conventions

- **Loading**: `loading` boolean + centered `CircularProgress`. No global spinner system.
- **Feedback**: local `error`/`success` string state → inline MUI `Alert`. **No Snackbar/toast anywhere in the app.**
- **Forms**: plain controlled state, no form library (no Formik/RHF); validation is HTML5 `required` + manual pre-submit checks, not a client-side schema validator.
- **Dirty-tracking**: settings-style pages keep current + original state, `isDirty` via `useMemo`, Save/Cancel only when dirty.
- **Dialogs**: `Dialog`/`DialogTitle`/`DialogContent`/`DialogActions` for all create/edit forms. Recurring "invite link" sub-pattern: dialog swaps to a read-only shareable-link view on success instead of closing, when email isn't actually sent.
- **Tables**: MUI `Table`+`Paper`, `Chip`s for status/tags. `Quotations.jsx`, `PolicyApplications.jsx`, `PolicyApproval.jsx`, `EndorsementApproval.jsx`, `ClientPolicies.jsx`, `Clients.jsx`, `InLeaseBacklogs.jsx`, and `AccountingTransactions.jsx` are server-side paginated (`TablePagination`); others load everything at once.
- **Streamlined tracker table columns** (standing convention as of the Quotations/PolicyApplications/PolicyApproval/EndorsementApproval/ClientPoliciesTable/Accounting pass — **apply this to every future tracker-style table, including the Accounting one, rather than reverting to one-column-per-field**): a reference number column (`Quotation #`/`Application #`/`Endorsement #`/`Policy #`) is set in `sx={{ fontFamily: "monospace", whiteSpace: "nowrap" }}` for easier scanning; `Class`+`Product Variant` collapse into one **Class / Variant** cell (`Typography variant="body2"` over `variant="caption" color="text.secondary"`, stacked); a start/end date pair (`Insured From`/`Insured To`, `Effective`/`Expiry`) collapses into one **Coverage Period** cell rendered `"<start> – <end>"` with `whiteSpace: "nowrap"`; a long-value status/type chip that would otherwise stretch its column (e.g. a quotation's "For Issuance"/"Policy Issued" state) keeps a short, fixed label and moves the actual identifying value (an application/policy number) into a `Tooltip` instead of the chip's own text. These trims exist because the un-collapsed versions measurably widened these tables past a comfortable read width — not a purely cosmetic choice, so don't reintroduce the split columns "for clarity" without re-checking that reasoning.
- **Search/filter bar** (`Quotations.jsx`, `PolicyApplications.jsx`, `PolicyApproval.jsx`, `ClientPolicies.jsx`, `Clients.jsx`, `InLeaseBacklogs.jsx`): a `Paper` above the table holding a free-text `search` field plus one or two status/type `Select`s, all server-side (see each route's own `list*QuerySchema` — `search` does a case-insensitive `OR` across that record's own number, insured name, and — `PolicyApproval.jsx` only — filing agent code/name; status/type/`policy_status` map straight onto their real columns except a quotation's own `status`, which is derived from `converted_application` the same way the row data already is). `search` is debounced 300ms (a local `search` state feeds a `debouncedSearch` used in the actual fetch) so it doesn't re-fetch on every keystroke; every filter resets `page` back to `0` synchronously in its own setter (never via a separate effect keyed on the filter values — that would double-fetch, once at the stale page and again once it resets) since a narrower result set could otherwise leave the table stuck on an out-of-range page. A "Clear filters" button appears only once any filter is actually set (`hasActiveFilters`), and the table's own empty-state row swaps to a "no results match" message while any filter is active. Status/type option lists are drawn from existing shared/local label maps (`components/StatusChip.jsx`'s exported `STATUS_LABELS`, each page's own `POLICY_TYPE_LABELS`/`POLICY_STATUS_LABELS`) rather than a fourth copy. Deliberately no "Class" filter despite the schema supporting `class_id` — populating that dropdown would need a classes-list fetch, and no single endpoint both requires the right permission on all four pages and returns a light-enough payload (`GET /product-catalog` needs `CREATE_APPLICATION`, `GET /insurance-classes` needs `MANAGE_SETTINGS.MANAGE_PRODUCTS`, neither of which every viewer of these tables necessarily holds) — left as backend-only for now.
- **Printing/PDF**: there is exactly one implementation of each document's layout — the corresponding PDFKit builder in `backend/src/pdf/` — used for the on-screen preview, the download, and the email attachment alike. No `window.print()`/`#print-root` portal (removed; `index.html` has no print CSS), and no separate HTML preview component either (an earlier version of this had both `PolicySchedulePreview.jsx`, an HTML/CSS mockup, *and* the PDFKit files, which meant editing a layout in two different rendering systems to keep them in sync — that component was deleted once the dialogs switched to embedding the real PDF instead of a lookalike). Every preview/export flow follows the same shape: `fetch()` the PDF as a `Blob` (a `previewXPdf`/`downloadXPdf` function in `api/client.js`, via `requestBlob` — needed because these endpoints require an `Authorization` header, which a plain `<iframe src="...">` can't attach), `URL.createObjectURL()` it, hand the resulting URL to `components/PdfViewer.jsx` for inline display (rendered via `pdfjs-dist` onto `<canvas>` — see PdfViewer.jsx's own entry above for why not a native-plugin `<iframe>`), and reuse that *same* URL for the "Print / Save as PDF"/"Re-export PDF" button (`window.open(url, "_blank")` — synchronous, since the blob is already in hand by the time the button is clickable, so there's no popup-blocker timing issue to work around and no second network request).
- **Wizard/linear-disclosure**: `PolicyApplication`/`QuotationCreator` reveal each section only once the prior section's completeness check passes.

## Local dev DB reference

`backend/.env` has `DATABASE_URL`, `PORT`, `JWT_SECRET`, `JWT_EXPIRES_IN`, `FRONTEND_URL`, and commented `SMTP_HOST/PORT/USER/PASS/FROM` placeholders (fill in to make quotation "Resend to client" actually send). No `.env.example` file exists.

**Migration-timestamp gotcha**: several existing migration folders in `backend/prisma/migrations/` carry hand-picked, round-numbered timestamps (`..._120000_...`, `..._150000_...`, `..._180000_...`) rather than genuine `prisma migrate dev` auto-generated ones, and the container's own system clock has been observed running *behind* where those hand-picked timestamps land on the same simulated date. A brand-new `prisma migrate dev` migration gets its folder name from the container's real clock at that moment — if that's earlier than the last hand-picked one, the new migration silently sorts *before* migrations it actually depends on (e.g. a migration adding a FK to a table another migration creates), and a later `prisma migrate dev` run fails shadow-database replay with a "relation does not exist" `P3006` error, even though the migration already applied fine to the real dev DB. This has already happened twice in this project's history (`add_endorsement_inlease_link`, `add_agent_payable_transaction`). **If this happens again**: `docker exec policyissuance-backend-1 date -u` to see the container's real clock, `ls prisma/migrations | sort` to find the true last-in-order migration, then `mv` the offending folder to a timestamp that sorts after it and run `UPDATE "_prisma_migrations" SET migration_name = '<new folder name>' WHERE migration_name = '<old folder name>'` against the dev DB so Prisma's own tracking matches. Also note `prisma migrate dev` refuses to run at all in this non-interactive shell whenever it needs to warn about a destructic change (e.g. removing an enum value) — for those, use `prisma migrate diff --from-config-datasource --to-schema prisma/schema --script` to get the SQL, hand-assemble a migration folder with it (add any extra raw SQL, like a `CHECK` constraint Prisma can't express in schema.prisma), apply with `prisma db execute --file <path>`, and insert the matching `_prisma_migrations` row yourself (`checksum` can just be `'manual'` — nothing re-validates it locally).
